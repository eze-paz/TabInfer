# reference_qwen3-dense-webgpu-variants

> Dense-Qwen3 WebGPU catalog + the trap that Qwen/Qwen3-2B is NOT a dense model

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

The hand-written WebGPU engine ([[project_sandpie-webgpu-engine]], modules/webgpu-qwen3.js) runs ONLY **dense `Qwen3ForCausalLM`** models — same kernel set, just different dims. It CANNOT run hybrid/gated-DeltaNet (linear_attention) or multimodal arches.

**TRAP (cost a "Array buffer allocation failed" bug 2026-06-24):** `Qwen/Qwen3-2B` EXISTS on HF but is **`Qwen3_5ForConditionalGeneration`** — a Qwen3.5-VL multimodal model with `linear_attention` (gated DeltaNet) layers + `head_dim: 256`. NOT dense, NOT runnable here. There is **no dense Qwen3-2B**. Dense Qwen3 sizes = 0.6B, 1.7B, 4B, 8B, 14B, 32B (+MoE). Always check `config.json` `architectures` + `model_type` before adding a variant.

**Current dense catalog (commit 5ac3d8d, webgpu-qwen3.js v75):**
- `'0.6B'` — 28L/h1024/16q-8kv/hd128/inter3072/vocab151936, single `model.safetensors`, ~1.1GB
- `'1.7B'` — 28L/h2048/16q-8kv/hd128/inter6144/vocab151936, **sharded** (2 shards, 3.28GB+0.59GB BF16), ~3.9GB
- (4B = 36L/h2560/32q-8kv/inter9728 — compatible if ever added)

**Engine wiring:** `CONFIGS`/`MODEL_ROOTS` maps keyed by variant; `CONFIG` mutated in-place on switch (keeps all `CONFIG.xxx` refs valid); `loadModel({variant})` unloads+reloads on change; `variant()` accessor; `runConversation` reads the variant from **`provider.endpoint`** (the model picker stores modelId there via spEndpoint — NOT `provider.modelId`). Shard-aware loader fetches `model.safetensors.index.json` first, falls back to single `model.safetensors`.

**Decode kernel-fusion campaign (motivated by arXiv 2604.02344 "WebGPU Dispatch Overhead"): batch=1 decode on this iGPU is bound by per-dispatch CPU overhead (~60µs ea on low-power iGPU, `submit` = 40% of it), so CUTTING DISPATCHES/token beats faster kernels (faster kernels gave <5% end-to-end in the paper; fusion +53%). Plan: reduce per-layer decode dispatches.**
- **Fusion #1 SHIPPED (commit ab9aeef, webgpu-qwen3.js v93): quantize q/k/v activation ONCE.** q/k/v projections all read the same rmsnorm output, but `gemvDP4A` quantizes its input internally → the identical vector was quantized 3×/layer. Split `gemvDP4A` → `quantQ8(x,K)` + `gemvDP4_only(pack,sc,y,N,K,acc)`; decode path (T=1) runs quantQ8 once then 3 gemvs. Saves 2 dispatches/layer (~56/token). PROVABLY identical output (same kernels/data); prefill (T>1) + `__noDp4` unchanged; `__noQkvFuse` disables for A/B. VERIFIED 0.6B in harness: greedy output BYTE-IDENTICAL fused vs unfused; interleaved best-of-6 decode 21.6 vs 18.1 tok/s (≈+20%, directional only — this iGPU thermally collapses 21→2 tok/s mid-run, wall-clock ±50%, so trust "faster + identical", not the exact %). MEASUREMENT GOTCHA re-confirmed: naive sequential A/B showed fused 26 vs unfused 37 (fused ran FIRST on cold GPU) — run-order confound; must INTERLEAVE + take best (least-throttled).
- **Fusion #2 SHIPPED (commit d8f63d8, webgpu-qwen3.js v94): fold int8 quantize INTO rmsnorm (`rmsnormQ`).** New kernel emits per-group int8 DIRECTLY from the norm (output layout bit-identical to rmsnorm→QUANTQ8: xq[g*8+k]=pack4xI8, xs[g]=scale; normed=x*inv*w recomputed INLINE during quantize → no shared-mem array, no hidden-size cap; one workgroup/row). Decode (T=1) uses it for BOTH the attention input norm (→ q/k/v via `gemvDP4_only`) and the MLP post-attn norm (→ `gateUpSiluDP4_only`), removing the separate quantize dispatch in both. Split `gateUpSiluQ` → `quantQ8`+`gateUpSiluDP4_only`. `__noRmsFuse` isolates for A/B; prefill (T>1) + f32 `__noDp4` paths unchanged. VERIFIED: new `selfTestKernels` 'rmsnormQ' test (NO model load — compares dequant vs CPU rmsnorm) err=0.0036 (int8 tol); full-forward 0.6B output byte-identical to fusion-#1 path; interleaved A/B ON>OFF in all 6 pairs (iGPU was deep-throttled 2-5 tok/s that run, so % unreliable — direction only). Combined #1+#2 remove ~4 dispatches/layer (~112/token) vs pre-fusion baseline. **FLAGS REMOVED (commit 7b148ab): decode (T=1) is now UNCONDITIONALLY the fused int8 path — `__noQkvFuse`/`__noRmsFuse`/the decode `__noDp4` branches are gone (user wanted the pure fused model, no toggles). Prefill (T>1) unchanged; linearQ's internal `__noDp4`/`__noDp4Gemm` selectors remain.** If a fused-decode regression surfaces, there's no longer a runtime toggle — revert via git or re-add a branch.
- **Next levers (not yet done):** q/k/v projection MERGE into one kernel (paper found K+V merge ~negligible +0.5%, low priority). rope fusion. The big remaining decode cost at LONG context is the attention KV-scan (separate from dispatch overhead) — KV quantization (q8 KV) is the untried lever there (f16 KV + split-KV already tried+reverted).

**THE "!!!!" GARBAGE AT CONTEXT >4096 = decode-attention sc[] OVERFLOW (commit 3b81255, v103) — the REAL root cause after several wrong turns (OOM theory was WRONG).** Stress-tested runConversation at rising prompt sizes: coherent at L=4026, garbage at L=5354 → collapse exactly at S>4096. Cause: `ATTN_DEC_WGSL` (decode T=1 attention) had a HARDCODED `var<workgroup> sc : array<f32, 4096>` (one score per key); it writes `sc[key]` for every key<S, so S>4096 → OUT-OF-BOUNDS shared-mem write → corruption → "!!!!". Never surfaced before because MAX_SEQ was pinned ≤4096; the auto-grow/configurable-context work let S exceed 4096 → straight into the overflow. PREFILL flash-attn (ATTN_WGSL) is FINE (tiles K/V, no S-sized array) — only DECODE overflowed. FIX: device-adaptive MAXS — `ATTN_DEC_WGSL` → `attnDecWgsl()` baking `MAXS=${_attnMaxS}`; `_attnMaxS` sized at load from `E.device().limits.maxComputeWorkgroupStorageSize` (sc is f32 so MAXS*4 + ~3KB qd/red/part must fit; 32KB gen-12lp → 7168). `_ctxCap` clamped to `_attnMaxS` so S can't exceed sc; pipeline label includes `_attnMaxS` (no stale-size reuse). Verified: L=4778/5802/6426 all coherent. **HARD CEILING now ~7168 on a 32KB iGPU — CANNOT reach 8192 with the sc-array design (sc alone = 32KB). True 8192 needs a TILED/STREAMING decode attention (online softmax over key-tiles, no S-sized array, like the prefill kernel) — pending follow-up.** Methodology win: the user said "stress test to find where it collapses and why" — driving runConversation at rising L + classifying garbage pinpointed S=4096 in minutes; the static OOM guesses had been wrong.

**maxTokens default bug + configurable context (commit 71da8d3, webgpu-qwen3.js v92):** Symptom a user hit — a reasoning turn (1.7B) emitted a `<think>` stream then NO answer/tool call, looked like a parse bug but wasn't. Cause: `runConversation`'s per-round generation budget defaulted to **512** tokens; a Qwen3 `<think>` block routinely overruns 512 → decode hit the cap mid-thought (before `</think>`+answer), so `parser.content` was empty + no tool calls → agent loop ended. The parser/EOS are fine (`STOP`=im_end|endoftext stops finished turns; the model simply wasn't finished). FIX (final, commit 7b148ab): NO artificial cap — `maxTokens` defaults to **MAX_SEQ** (the context window), since any fixed cap truncated long reasoning (512 then 2048 both did). EOS (im_end) stops finished turns; context is the sole bound (decode loop hard-caps at MAX_SEQ-1-pos). `provider.maxTokens` ("Max output tokens") overrides for a tighter cap. CONTEXT-WINDOW BUG (REAL cause, fixed commit 35a6704, v101): provider.contextWindow=8192 was IGNORED (MAX_SEQ stuck at 4096) because of MY loadModel resize logic, NOT a user/field error (I wrongly blamed "wrong field" first — the user had both fields at 8192; trace the call sites before blaming config). `loadModel` had THREE call sites: runConversation passes `nCtx: provider.contextWindow` (sets MAX_SEQ=8192), but `_streamIds` (line ~2651) and `generate` (~2436) call `loadModel({variant})` with NO nCtx on every prefill → my resize logic clamped undefined→4096 and, since 4096 !== 8192, SHRANK MAX_SEQ back to 4096 + freed KV every prefill. FIX: nCtx is optional — omitted/0 = "keep current window"; only an explicit positive nCtx resizes MAX_SEQ. So nCtx-less calls never shrink it and runConversation's value sticks. ALSO (commit 479f5db, v100) `_streamIds` AUTO-GROWS MAX_SEQ to fit `prompt+1024` (clamped 8192, via `_growCtx`) instead of throwing "prompt too long" — safety net independent of config. Plumbing is fine (providers.js spContextWindow→p.contextWindow→getActive→runConversation→loadModel nCtx). **THEN 8192 produced "!!!!" GARBAGE = iGPU OOM (commit 3d15208, v102): ensureKv PREALLOCATED the full window (~1.9GB f32 KV; geometry identical 0.6B/1.7B), overflowing the iGPU → corrupt reads (kernels are MAX_SEQ-agnostic, so NOT a kernel bug). FIX = LAZY SIZING: provider.contextWindow is now only the growth CEILING (`_ctxCap` ≤ CTX_HARD_MAX 8192); MAX_SEQ starts 4096 and auto-grow expands it to JUST fit prompt+1024 (capped at _ctxCap), so a 4212-tok prompt allocates ~5236 (~1.2GB) not 8192 (~1.9GB). loadModel only sets _ctxCap; unload resets MAX_SEQ=4096. LESSON: never preallocate the configured-max KV on a memory-tight iGPU — size to the actual prompt; ~2GB works / ~3GB garbages (1.7B) ≈ the iGPU mem budget.** Also made context size CONFIGURABLE: `MAX_SEQ` is now a `let` (was `const 4096`) set in `loadModel({nCtx})` from `provider.contextWindow` (clamped 1024..8192, default 4096); a ctx change on an already-loaded model just frees+reallocs the KV buffers (weights untouched). MAX_SEQ does NOT bound any workgroup shared-mem array (the "ATTN_MAXK = MAX_SEQ" comment is STALE — flash attn streams K/V in tiles), so raising it only costs KV memory (f32, ~0.9GB at 4096 for the shared 28L×8kv×128 geometry). providers.js: `applyTypeUI` now `show('spContextWindow', true)` (was hidden for webgpu — "fixed ctx") + relabels it "Context size" for webgpu; "Max output tokens" (spMaxTokens) was already visible. Verified in-browser: webgpu type shows both inputs. (Version chain: qwen3 91→92, worker 8→9, host 11→12, providers 30→31.)

**Prefill perf — MEASURED 2026-06-24 (don't re-litigate):** Decomposed a real 0.6B prefill (GPU-synced wall clock, 256-tok chunks): at LOW context ~256 keys = **229 tok/s** (the fixed GEMM+MLP+rope+norm cost) — *faster than llama.cpp Vulkan's 203 tok/s for full 0.6B*, so our prefill GEMM is NOT uncompetitive. At ~2048 context the attention delta (+1057ms) ≈ the entire fixed cost (1120ms): **attention is ~half of long-context prefill and grows O(T²)**. The "64 tok/s" complaint was 1.7B-at-3472 (bigger model × long ctx × FIRST turn — and first-turn only now that the prefix cache landed). Prefill attention kernel (q3.attnFlash) is ALREADY vec4-optimized + causal early-exit (the 3.4× win is ported). gemmQ ≈ 193 GFLOP/s f16-tile.

**System-prompt cache = in-memory KV ANCHOR (commit db29f7a, webgpu-qwen3.js v99) — the REPLACEMENT for the removed disk cache.** Insight: the system block (system prompt + tool descs + skill defs + skill guidance, all concatenated into `sys`) is an identical token prefix across every conversation; once prefilled its KV sits in `_kv[0..P_sys)` and is NEVER overwritten (decode writes [L..); later prefills start at [P_sys..)). So instead of snapshotting/copying, just RECORD it: `_sysAnchor = {variant, ids}` = "_kv[0..ids.length) holds this exact system block's KV". `_sysCacheClaim` (before round-0 prefill): if anchor matches the incoming system block AND the live `_cachedIds` doesn't already cover it, set `_cachedIds = sysIds` so `_streamIds` prefills only the tail — skips the system block even on a NEW conversation's first message (the case the disk path always failed). `_sysCacheRecord` (after round-0): refresh anchor. Cacheable prefix = system block ONLY via `TOK.encodeChat([{role:'system',content:sys}], {addGenerationPrompt:false})`. ZERO copy / disk / extra GPU mem / eviction. Invalidated wherever `_kv[0..P_sys)` could be clobbered: model switch + ctx resize, `generate()` (prefills from 0), `unload`, prefill-abort. RoPE-correct (system always at pos 0..P_sys-1). IN-MEMORY ONLY: does NOT survive page reload — the FIRST conversation after a load prefills the system once to populate the anchor, every conversation after reuses it. NOT runtime-verified yet (preview port held + flaky model load); logic is a strict superset of the proven `_cachedIds` reuse so low risk.

**Quantized-weights cache (commit 24fbbee, webgpu-qwen3.js v83):** Stop caching raw safetensors + re-quantizing every load (~40s). First load streams each tensor's GPU-ready bytes (int4 pack+scales / f16) via a sink into fixed 64MB Cache Storage chunks (`sandpie-webgpu-quant`, keys `https://sandpie.quant/v<QCACHE_VER>/<variant>/c<i>` + `/manifest`), each segment 16-aligned so reader writeBuffer slices are 4-aligned; manifest written LAST = commit point (deleted first). Warm load (`loadQuantCache`) reads manifest → allocates all GPU buffers → reads chunks in PARALLEL (QREAD_CONC=4) → writeBuffer slices STRAIGHT to GPU (peak host ~256MB, no whole-model staging, no re-download, no re-quantize). Validated by ver/variant/qgroup/config; graceful cold fallback (re-download+rebuild) on miss/mismatch/eviction; QCACHE_VER bumps invalidate. Raw-safetensors cache REMOVED (fetchModelBytes/_fetchShardChunks are pure downloaders now). VERIFIED 0.6B: cold writes 10 chunks/617MB; warm load **2.4s** (phases cache→parse, no download), coherent. (Preview sandbox evicts Cache Storage under transient pressure → cold write can lose chunks mid-build while the old raw cache frees; fallback handles it; prod persistent storage is fine.) clearLocalModelCaches (providers.js) only deletes litertlm — does NOT clear webgpu caches (pre-existing gap; rely on QCACHE_VER).

**Deep GPU clean on backend switch (commit 1a75f22):** Gemma↔Qwen switching used to leave BOTH backends' weights+KV resident (overload) — LiteRT's single-active unload called the DELETED TabInferQwen35 not TabInferQwen3, and the Qwen3 host shim unloaded nothing. **DP4A prefill GEMM — codegen-unroll fix + why it's still off (commit f1fc642):** WebGPU can't use coop-matrix on this box: gen-12lp has NO matrix HW (XMX is Arc+), its Vulkan coopmat is DP4A-backed, and WebGPU `chromium-experimental-subgroup-matrix` is gated to the Vulkan backend (Dawn doesn't do it on D3D12, which is what Chrome/Windows uses) + targets Arc XMX. BUT WebGPU has the same primitive: `dot4I8Packed` (native DP4A on gen-12lp). The old gemmDP4A was 0.58× because it used `array<>` accumulators (WGSL spills them — same trap as the naive f16 port). Rewrote codegen-unrolled (`gemmdp4Wgsl`, 64×64/BK=QGROUP=32, static i0..15 int32 + f0..15 f32, dot4I8Packed). Now wins on big matmuls (down/q ~1.2-1.5×), LOSES on small (k/v N=1024 ~0.5×) because it quantizes the activation PER CALL — fixed pre-pass dominates a small GEMM. Wall-clock bench noise is ±50% on this throttling iGPU (gate swung 0.69-1.34 same kernel) → no clean verdict; need GPU-timestamp min-of-N. Kept behind `__useDp4Gemm` (default OFF). To realize the win: FUSE the activation quantize (quantize the rmsnorm output ONCE, reuse for q/k/v — q/k/v share s.normed) + GPU-timestamp A/B. 1.7B prefill profile: GEMM ~66% / attention ~34% (attn ~57 GFLOP/s, <5% peak — the cleaner next lever). DP4A may win cleanly on mobile (Adreno native DP4A).

**Prefill speed (0.6B, computed from kernel benchmarks 2026-06-25, NOT flat 200 tok/s):** declines with prompt size (attention is O(T²)). 0.6B ≈ 185/170/155 tok/s at 2000/2500/3000; 1.7B ≈ 110/105/100 (wider GEMMs, same KV/attention). gemmQ per 256-tok chunk: 0.6B ~727ms (28L×~26ms), 1.7B ~1.7s. attention (28L, 256 q-chunk): ~6ms@256keys → ~56ms@3072keys. The "200 tok/s" was llama.cpp's 1.7B Vulkan figure; ours hits ~200 only for 0.6B at small ctx. Ground truth = the `[qwen3 perf] prompt=N … prefill=Xs (Y tok/s)` console line (Y = NON-cached tokens/s).

**Focused-tab decode collapse — REAL root cause = backdrop-filter compositor competition (commit 140f875):** After the worker (c863d09) AND deep-pipeline (120aa89) BOTH failed to fix focused=20%/backgrounded=100% GPU, compared against the reference engine `webml-community/gemma-4-webgpu-kernels` (downloaded its 552KB gemma-4-e2b.js, grepped the loop). Reference = MAIN thread, reads back EVERY token via mapAsync in a depth-4 pipeline (`async function*wo`, `vo=4`, `submitStep`→`readTensor`→mapAsync), WITH a heavy Three.js compositing background — yet FAST focused. So: decode-loop technique is fine (ours matches), main-vs-worker irrelevant, foreground compositing per se doesn't throttle. The differentiator = OUR CSS: 8+ `backdrop-filter:blur()` (sidebar, the chat FORM over the message area, panels, modals) + infinite anims (auroraPulse). backdrop-filter:blur RECOMPUTES every frame the content behind it changes = every streamed token → GPU process burns its budget on blurs → WebGPU compute starved (~20%); backgrounded = no compositing → 100%. Reference has NO blur over changing DOM. FIX (no engine/conversations.js change): webgpu-host.js adds `body.sp-decoding` (ref-counted) around a run; sandpie.css `body.sp-decoding * { backdrop-filter:none!important; animation-play-state:paused!important }` (one recalc/message). Verified: blur(16px)→none under the class. **Lesson: the worker + readback-pipelining were RED HERRINGS — measure against a known-fast reference EARLY. Decisive control = the bare test harness (docs/, no backdrop-filter) runs the SAME engine fast focused.** Can only confirm focused win on a real focused tab (headless preview = backgrounded).

**[SUPERSEDED theory] Focused-tab decode throttle = vsync-paced readback, NOT JS contention (commit 120aa89):** Even with the engine in a worker, decode stayed ~3.4× slower focused vs backgrounded (2.9 vs 9.8 tok/s @3200 ctx), GPU ~20% (idle) focused / 100% backgrounded. The worker proved it's NOT main-thread JS contention. ROOT CAUSE (research-confirmed): the decode loop's only yield — the per-batch `await mapAsync()` readback — has its RESOLUTION paced to the compositor/vsync (Dawn device tick on BeginFrame) when the tab is VISIBLE + contended by foreground rendering; backgrounded relaxes it → GPU saturates. "Awaiting mapAsync between dispatches idles the GPU" is a documented WebGPU pitfall. The loop was already depth-2 pipelined but one in-flight batch can't hide a readback that resolves far slower than its compute when focused. FIX: GEN_BATCH 8→32 (4× fewer readback syncs; each token still its OWN bounded submit, NO TDR — only readback frequency drops) + PIPE_DEPTH=3 batches in flight (FIFO, GPU never idles on a readback) + stop/abort halts emit immediately discarding ≤PIPE_DEPTH-1 queued batches. **Can only confirm the focused win on a REAL focused tab — headless preview = effectively backgrounded, so it shows the fast path regardless.** If still throttled focused, the secondary lever is foreground COMPOSITOR GPU competition (streaming-text repaints + aurora backdrop-filter re-evaluating every frame) — test by switching to a no-backdrop-filter theme / collapsing the sidebar during decode; mitigate by throttling DOM repaint rate during local inference.

**Fast int4 GEMM ported to dense prefill (v81, commit 72b3541) — the REAL prefill win:** CORRECTION to the earlier "prefill competitive" claim: 0.6B and 1.7B share KV geometry (both 28L×8kv×128hd → 112 KiB/tok), so KV size can NOT distinguish them; the llama.cpp log WAS 1.7B and the ~3× gap (ours 64 vs llama.cpp Vulkan 203 tok/s) is REAL + apples-to-apples. Root cause: the dense engine's gemmQ was an OLD 128×32/BK16/f32-scalar kernel (~193 GFLOP/s) while the deleted Qwen3.5 fork had a 64×64/BK=32 f16-tile kernel measured ~548 GFLOP/s on THIS gen-12lp. Recovered it from git (`git show 4993ee9~1:modules/webgpu-qwen35.js`, fn `gemmqWgsl`) and ported verbatim. **KEY: accumulators must be codegen-UNROLLED to static scalars (acc0..15) — a WGSL `array<>` spills to memory; a naive array-based vectorize measured 84 GFLOP/s, SLOWER than the f32 original (a trap I hit first).** f16-dot picked by `probeF16Gemm` at load (defaults caps.hasF16; falls back to f32 if a GPU computes f16 wrong); bank-pad OFF (10% regression on gen-12lp). MEASURED A/B: 1.7B q 4.5× (496 GFLOP/s), 1.7B gate 2.8× (586), 1.7B down 1.4×, 0.6B gate 1.9×; self-tests pass (rel 4.8e-4, tol now RELATIVE 3e-2 since f16 shared tiles round ~0.3%), generation coherent. Wide 1.7B matmuls (q/gate) gain most = the shapes that dominate 1.7B prefill.

**Prefix cache across turns (v77, commit 0553151):** The dense engine re-prefilled the WHOLE prompt every turn (a 3000-tok system prompt = ~54s before each reply) even though KV buffers persist — it just always restarted prefill at pos 0. The Qwen3.5 fork had prefix caching; this path didn't. Fix: `_cachedIds` = token seq resident in KV[0..len); `_streamIds` finds the longest shared leading run with the new prompt and prefills only the tail (shared tokens are at the same absolute positions → RoPE-exact KV reuse), always running ≥ the final token for fresh decode-start logits. Decode writes KV[L..) which never touches the prefix, so the next turn (chat template appends after the current assistant turn) cleanly extends it. `_cachedIds` nulled on prefill-abort / unload / generate(). VERIFIED bit-exact (same-prompt-twice byte-identical, prefill 204→1 tok; extended turn output == full fresh prefill).

**Big-shard loading (v76, commit cc018a1) — the "Array buffer allocation failed" fix:** Qwen3-1.7B's first shard is **3.28GB**, which the JS heap won't hand out as ONE contiguous `Uint8Array` on a 16GB box → that exact error. Fix = hold each shard as a **LIST of small chunks** (every alloc tiny, total fine in RAM) + read each tensor's byte-range ACROSS chunks (`_chunkReader`, binary-search + cross-boundary copy; verified bit-exact over 4000 random ranges). Helpers: `_uploadTensor` (shared per-tensor quantize/f16+GPU upload), `_streamToChunks`, `_fetchShardChunks` (best-effort Cache Storage read/write via Blob — no contiguous alloc), `_parseSafetensorsChunks`. Single-file 0.6B still uses the in-RAM `_parseSafetensors`. **REJECTED: OPFS/CacheStorage write-through** — needs that many GB of *storage* quota, which is TIGHTER than RAM (preview sandbox quota = only 3.46GB < the 3.28GB shard). RAM-bound chunk list sidesteps quota entirely. VERIFIED in-browser: 1.7B downloads 3.9GB + reaches parse phase with no alloc error; 0.6B still coherent.
