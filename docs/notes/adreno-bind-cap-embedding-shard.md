# adreno-batched-encoder-broken

> Adreno all-\"!\" TRUE root cause = embed matrix (297MB) exceeds 128MB storage-buffer bind limit; shard it. Batching/DP4A/f16 were red herrings.

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

## TRUE ROOT CAUSE (found via _stageProbe, engine v52 / qwen3 v134, 2026-07-08)
The embed matrix exceeds `maxStorageBufferBindingSize`. Qwen3-0.6B embed = vocab 151936 × H 1024 × 2B (f16) ≈ **297MB**; Adreno caps the storage-buffer bind size at **128MB**. The buffer can be created + copyBufferToBuffer'd (readback showed nonzero BYTES → misleading), but **binding it to a shader reads ZERO** → embed output all-zero → whole forward zero → argmax 0 → "!". Desktop bind limits are GBs → only failed on mobile. Per-kernel conformance missed it (tiny buffers). lm_head is int4 (~78MB) so it already fit.
FIX: `_shardEmbedIfNeeded()` splits the embed f16 buffer into ≤95%-of-limit row-shards via `copyBufferToBuffer` (copy has NO bind limit), destroys the oversized original; shard-aware `EMBED_SH_WGSL` (EMBED_SHARDS=6) binds all shards, selects per row (`row/shardRows`). Only activates over-limit; desktop keeps single-buffer fast path. Test override `globalThis.__embedShardLimit`. VERIFIED end-to-end on Iris (forced 100MB → 4 shards → coherent gen "\<think\> Okay, the user is asking for the capital of"). Phone 128MB → 3 shards.
DIAGNOSTIC THAT NAILED IT: `_stageProbe()` (purple test-page button) taps nonzero-count after each forward stage (layer 0) → `firstZero=embed`. LESSON: build a stage-walk probe FIRST; don't hypothesize (burned ~4 wrong fixes: DP4A, f16, batch-probe v48/v49, vendor gate).

## ADRENO PERF: dot4I8Packed is SOFTWARE-EMULATED (qwen3 v138, 2026-07-08)
After the all-"!" fix, prefill was ~20× below the FLOP ceiling (2800-tok prefill >2min; ~18 GFLOP/s). Cause: Adreno emulates `dot4I8Packed` in software. On-device A/B at the down_proj shape (256×1024×3072): int4 DP4A **19 GF/s** vs f16 gemmQ **106 GF/s** — f16 is 5.5× faster (Iris opposite: DP4A 537 vs f16 424). FIX: `probeDp4()` now also TIMES gemmDP4A vs f16 gemmQ at load; if f16 wins by >1.3× it sets `__noDp4Gemm`+`__noDp4` → prefill AND decode use gemmQ/gemvQ (f16). `__forceDp4=true` overrides. `_benchPrefillGemm()` + green "Prefill GEMM A/B" test-page button. GOTCHA: probe shape MUST be the real bottleneck shape — a small shape (64×512×1024) misleads because DP4A's activation-quantize overhead dominates there and wrongly disables DP4A on desktop. Remaining gap vs LiteRT = subgroup-matrix + texture operands (bigger project); and the 2800-tok prompt itself (system prompt+tools) is half the first-token latency. NOTE: comparison target is litert.js (their WebGPU web build), NOT the Kotlin/native-OpenCL one — so their edge is better WebGPU kernels + MTP speculative decode, which IS matchable.

## GEMM AUTOTUNER (qwen3 v141, prefill lever). f16 GEMM tiling (64x64/4x4) was Iris-tuned; other GPUs run it at a fraction of peak (Adreno f16 was only ~106 GF/s = ~10% of ALU peak → tiling/occupancy problem, not a wall). `gemmqWgsl` is now parametric over {BM,BN,TM,TN}; `autotuneGemmQ()` sweeps configs at the down_proj shape at load (ONLY when `__noDp4Gemm` = f16 path = mobile), VERIFIES each vs reference (correctness gate — never ship fast-but-wrong), keeps fastest into `_gemmCfg`. Reset on device rebuild; `__noGemmTune` disables; result in `_debugLogits.gemmTune` + `__gemmTuneResult`. Iris: 9 configs, picked 32x64/4x4 (247 GF/s, ~9% over default). WebGPU roofline: prefill = COMPUTE-bound (GEMM tiling is the lever), decode = BANDWIDTH-bound (~300MB int4/token ÷ 24GB/s ≈ 80 tok/s ceiling; lever there = speculative/multi-token decode ~2x, NOT kernel tuning). Research (arXiv 2605.20706 "Llamas on the Web") confirms f16>int4 on mobile + subgroup-matrix absent in stable browsers.

## RED HERRING (below, shipped but did NOT fix it): batched command encoder.
Original (wrong) theory: Adreno drops a `queue.writeBuffer` issued WHILE a command encoder is open (before its submit) — the submitted pass reads the stale/zero buffer. Every real kernel writes its uniform via `uniform()`→writeBuffer inside `beginBatch()`, so the whole batched forward reads mul/dims=0 → zero output. NOTE: a bare batched dispatch with NO in-batch writeBuffer WORKS (first probe was a false pass, batchOk=true yet embedOut still 0) — the probe MUST write a uniform inside the batch then read it (engine v49). The whole forward runs inside `E.beginBatch()/endBatch()` → all-zero hidden → all-zero logits → argmax 0 → "!". Every kernel passes conformance because those run as immediate per-op dispatches (which DO work on Adreno). FINAL FIX (SHIPPED engine v51, 2026-07-08): mobile DENYlist (v50) failed because Android Chrome REDACTS adapter vendor/architecture to "" inside the Web Worker where the engine actually runs (main-thread test page showed qualcomm/adreno; worker shows ""). So inverted to an ALLOWLIST: `_batchOk` defaults FALSE; batching turns ON only when adapter positively matches `intel|nvidia|geforce|rtx|gtx|amd|radeon|rdna|apple m[0-9]|microsoft|warp|mesa|llvmpipe|swiftshader` AND the probe passes. Empty/unknown/mobile → OFF → immediate per-op submits. Iris (intel) keeps batchOk=true, no regression. `globalThis.__forceBatch` overrides.

SUPERSEDED intermediate attempt (engine v50, 2026-07-08): the runtime probe kept FALSE-PASSING on Adreno (v48 no in-batch write; v49 with in-batch uniform write STILL passed yet real forward stayed zero), so pivoted to a DETERMINISTIC vendor gate in `probeBatch()`: adapter vendor/arch matching `qualcomm|adreno|mali|arm|powervr|img|apple-[am]|broadcom|vivante` → `_batchOk=false` → `beginBatch()` is a no-op → every `dispatch()` submits immediately (the per-op path all kernel self-tests pass on these GPUs). `globalThis.__forceBatch` true/false overrides. `E.batchOk()` exported; in `_debugLogits` flags. Reset on device loss. Desktop Intel/NVIDIA/AMD keep batching (Iris batchOk=true, no regression). VERIFIED END-TO-END on Iris with `__forceBatch=false`: coherent generation, not just nonzero buffers. LESSON: don't burn round-trips on a probe that can't reliably trip the bug when you already know the device — gate deterministically and verify the fix path locally by forcing the flag.
