# project_sandpie-local-runtime-strategy

> TabInfer in-browser backends — wllama=compat floor, WebLLM/LiteRT=GPU speed; don't fork wllama; no big MoE in-browser

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

Three wired in-browser LLM backends (provider `type` in providers.js; dispatch in agents.js runPrompt + conversations.js runConversation) — **webllm was REMOVED (commit `8525705`: webllm.js deleted + its `<script>` tag dropped); its bullet below is historical**:

- **wllama** — GGUF via llama.cpp WASM. Broadest compat (any GGUF, RWKV, ternary/BitNet TQ, runs on iOS Safari), CPU/WASM. The "runs anywhere" **floor**, not the speed champ: single-threaded until cross-origin isolation (COOP/COEP) is on; its WebGPU offload crashes. See [[reference_wllama-webgpu-crash]].
- **transformersjs** — ONNX, runs in a Web Worker. See [[reference_transformersjs-cpu-default]].
- **litertlm** — Gemma via Google LiteRT-LM, WebGPU, fast. See [[reference_gemma4-litertlm-thinking]]. **Web SDK limitation (confirmed 2026-06-18): loads ONLY SentencePiece-tokenizer models (i.e. Gemma).** Community Qwen 3.5 / VibeThinker `.litertlm` builds (HuggingFace/BPE tokenizer, zlib-compressed) fail at load with `"Streaming HF_Tokenizer_Zlib section is not supported yet"`; `@litert-lm/core@0.13.1` is the latest published — no fix, and a `-web` filename can't change the tokenizer type. So **Qwen 3.5 in-browser = wllama GGUF, NOT LiteRT** (tried adding 3 LiteRT Qwen models, all removed in commit `39d40ae`).
- **webllm** — MLC, WebGPU, fast, general-purpose. **Wired 2026-06-15 (commit e36824a)**, pinned `@mlc-ai/web-llm@0.2.84` (the build whose prebuiltAppConfig ships Qwen3.5/Qwen3/Gemma-3/Phi-4-mini). IIFE + `window.TabInferWebLLM`. Tools = native OpenAI `tools`/`tool_choice` with a `<tool_call>` prompt-parse fallback for non-FC models (Gemma). Thinking = live `<think>` split → reasoning channel + Qwen3 `/think|/no_think` soft-switch. WebGPU-only; weights cached in Cache Storage (not OPFS), so Dropbox sync can't see them. `listModels()` dumps the live catalog.

**Why:** the user keeps asking how to make local models faster / which models / "can we fork wllama like LiteRT".

**How to apply:** For "make local faster" — the real levers are (1) cross-origin isolation (COOP/COEP) to multi-thread wllama's CPU — **now ON in prod (2026-06-15, server-side; local/preview still single-thread)**, so wllama auto-threads (~6/12 cores) on the deployed instance — and (2) **route to a GPU runtime** (LiteRT for Gemma, WebLLM for general). Note: the "WebLLM ~10× slower than LiteRT on Gen12 Intel iGPU" claim is **UNVERIFIED folklore — no public benchmark backs it** (research 2026-06-19); Google's "10×" refers to NPU-vs-GPU on a MediaTek phone, not browsers/WebLLM. There is in fact NO published tokens/sec benchmark for ANY of these engines on an Intel Iris Xe iGPU — every public number is Apple Silicon or a discrete Intel Arc dGPU. Treat the LiteRT>WebLLM-on-iGPU belief as a hands-on impression, not fact. WebLLM remains genuinely unattractive for other reasons: WebGPU-only (no CPU fallback), no Qwen3.5, no Gemma 3/4, shares the TDR device-loss failure mode. wllama loads Qwen3 *dense* AND — **validated 2026-06-18 (commit `135a5d2`)** — **Qwen3.5 dense** (0.8B/2B/4B Q4_K_M now in the catalog; arch `qwen35`, hybrid Gated-DeltaNet; `delta_net`/`gated_delta` ops already in the WASM ≥3.4.1) on CPU/WASM, ~1.5–4 t/s single-thread localhost. Qwen3.5 emits thinking as `reasoning_content` (`streamRound` now forwards it to the Thinking box) and `/no_think` does NOT suppress it. Only the MoE Qwen3.5 (35B-A3B+) still can't fit in a tab. Do NOT fork wllama for speed: WASM caps at SIMD128 (no AVX), so it's inherently 2–4× under native and you won't beat llama.cpp's kernels. Big MoEs can't run in-browser at all: WASM32 ~4 GB ceiling + WebGPU device-memory cap, and the desktop expert-offload trick (`--n-cpu-moe` / `-ot`) has no in-browser equivalent — only small/dense (≤~9B) fits. See [[sandpie-project]], [[project_sandpie-module-architecture]].

**SINGLE ACTIVE LOCAL BACKEND — invariant (2026-06-18, commit `e846161`).** Only ONE local backend may hold a WebGPU/WASM context at a time. Two live WebGPU runtimes on a weak iGPU device-loss each other — confirmed by a log showing onnxruntime-web (transformersjs) AND `ggml_webgpu` (wllama) losing the device together (`A valid external Instance reference no longer exists`). Each backend exposes `unload()`: wllama → `_instance.exit()`, transformersjs → terminate its Worker, litertlm → `_engine.delete()`. Enforced two ways: (1) each `runConversation` `await`s the OTHER two backends' `unload()` before running (hard guarantee — one live GPU context during generation); (2) `applyActiveProvider` eagerly unloads non-active local backends on provider switch (a cloud provider frees all three). Tradeoff: switching backends reloads that model (the freed one re-inits lazily). **Do NOT introduce a second concurrently-live local WebGPU backend, and never remove the unload calls.** Companion change (commit `bef9e3d`): `applyTypeUI` gates Settings fields per backend so wllama-only load params (flash_attn / GPU layers / CPU threads / n_batch) no longer show for transformersjs/litertlm. Field matrix — wllama: all; transformersjs: maxTokens + frequency_penalty only; litertlm: contextWindow + temperature + reasoning + maxTokens.
