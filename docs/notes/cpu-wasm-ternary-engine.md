## ⚑ ROOFLINE — THE ENGINE IS ORCHESTRATION-BOUND, NOT SIMD-BOUND (2026-07-23). NEVER blame SIMD/kernel width again without checking this first.
Bonsai-1.7B decode, per token: **1.72 GMAC** (28 layers ×~50.3M q/k/v/o/gate/up/down + lm_head 311M) reading **~0.457 GB** weights (2.125 bpw). Three ceilings with 8 threads:
- **Compute (pure relaxed-dot, 16 MAC/instr, 8×~3GHz×1 dot/cy):** ~384 GMAC/s → **~220 tok/s**. (Real gemv_tern is only ~22% dot instrs → achievable-kernel compute ceiling ~90-100.)
- **Memory (0.457 GB/tok ÷ ~45 GB/s achievable):** **~90-110 tok/s** ← THE BINDING PHYSICAL CEILING.
- **We are at ~19 tok/s = ~5× BELOW the memory ceiling** (streaming only ~8.7 GB/s of ~45 available). So NOT compute-bound, NOT bandwidth-bound → **ORCHESTRATION-BOUND** (barrier ~80% of token). NB (corrected 2026-07-23): the ~141 wakes/tok are NOT the dominant cost — futex wake ~3-5µs → <1ms total; the barrier ~40ms is mostly worker gemv compute + main's own slice + contention, NOT wake latency. My earlier "wake ≈ half the token" was wrong.
IMPLICATIONS: (1) LUT/compute-reduction can't beat the ~100 memory ceiling and barely helps at 19 (overhead dominates). (2) WASM-128-bit-vs-native-256-bit gap only bites IF compute-bound — we're not. (3) The ~5× to the memory ceiling is orchestration overhead — BUT see next.
**⚑ EVIDENCE AUDIT (2026-07-23, user demanded incontrovertible proof) — turbo MECHANISM DISPROVEN, outcome holds:** Directly measured `% Processor Performance` (turbo) DURING synchronous gen bursts (immune to tab-throttle): park-fast AND hot-spin BOTH ~279-343% (~294% avg) — **hot-spin does NOT suppress turbo.** So my "spin kills P-core turbo" mechanism is WRONG/unconfirmed; I retract it. What IS incontrovertible + reproducible (back-to-back synchronous bursts, same box): **park spin400 = 13.76 tps > fuse = 11.84 > hot-spin spin250k = 11.33** — more spinning = slower, ~25%, every time. Mechanism = likely core/memory-bandwidth CONTENTION between spinning workers and main-thread serial JS (NOT turbo), but NOT cleanly isolated. ALSO incontrovertible: **orchestration-bound** = 13.76 tps × 0.457 GB/tok = **6.3 GB/s effective vs ~45 GB/s available (7× below memory wall)**; barrier ~80% of token (profiler). CAVEAT on prior claims: I did NOT cleanly decompose the barrier's ~40ms into wake-vs-compute-vs-contention (futex literature says wake ~3-5µs → 141 wakes ≈ <1ms, so the barrier is NOT wake-dominated as I'd guessed — it's mostly worker gemv compute + main's own slice + contention). Web research (SharedArrayBuffer/Atomics): no primitive beyond spin-then-park (adaptive futex = what we do); llama.cpp uses persistent spin-barriers + gets 14 tps < our park 19 → independent evidence park>spin here. SOFTENED CLAIM: park-fast is optimal AMONG TESTED sync strategies; spin-based fusion is dead; but "overhead is fundamentally intrinsic / 19 is THE ceiling" is NOT proven — an untested park-based per-layer barrier or tensor/throughput parallelism could differ.

**⚠️ (mechanism retracted above) ORCHESTRATION FUSION REGRESSED (2026-07-23).** Tried fusing qkv-gemv+attention into one dispatch via a WORKER-SIDE spin-barrier (PHASE ctrl slot, JOBTYPE=2, `qkvAttnFused`/`doAttn` refactor, `__fuse` flag) to cut a main round-trip (~28 wakes/tok). Output byte-IDENTICAL (41/41) but **SLOWER: 8.7 vs 11.8 tps**. ROOT CAUSE = the same turbo wall as every spin experiment: the worker-side barrier makes 8 workers HOT-SPIN waiting for each other + main's slice → kills P-core turbo → net worse than the park-round-trip it replaced. FUNDAMENTAL: every phase boundary needs a sync; on this chip a sync must PARK (~150µs wake, but turbo recovers) or SPIN (0 latency, kills turbo) — fusion just swaps a park for a spin-barrier and the spin's turbo cost > the saved wake. So the park-based round-trips are NEAR-OPTIMAL; the ~141 wakes/tok are NOT reducible by fusion. The roofline headroom is physically real but NOT reclaimable via sync-reduction on this hardware — it'd need a different execution model (throughput/batch parallelism across streams, or fewer intrinsic syncs). CONCLUSION: **~19 tok/s is close to the practical ceiling for the split-one-token-across-workers model on this turbo-sensitive chip.** Fusion kept behind `__fuse` (default off) as the documented negative result. Lesson: on 2P+8E, ANY spin (main OR worker-side) loses to park because turbo is the scarce resource.
