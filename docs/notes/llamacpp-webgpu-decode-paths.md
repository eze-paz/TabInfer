# reference_llamacpp-webgpu-decode-paths

> What llama.cpp's ggml-webgpu actually does on this Iris Xe gen-12lp (decode matmul + attention + KV dtype) vs our engine — the 3 levers, and why our split-KV failed

What llama.cpp picks on gen-12lp (supports_subgroups=true, supports_dot_product/DP4A=true, hasF16=true, **subgroup_matrix ABSENT**):
- **decode matmul (dst->ne[1]==1 → is_vec)**: `mul_mat_vec` + **MMVQ** = quantize activations to q8 then **DP4A int8 dot** (gated on supports_dot_product). We use `gemvQ` (int4 dequant in-shader, f32 math).
- **decode attention**: `flash_attn_vec` = **split-KV** (`flash_attn_vec_split` + `flash_attn_vec_reduce`) with **`subgroupAdd` reductions** (gated on supports_subgroups; vec path when `Q->ne[1] < MAX_SEQ`). We use `ATTN_DEC_WGSL` = single WG/head, manual shared-mem reduce, **no subgroups**.
- **KV cache dtype**: F16 **or even Q8_0/Q4_0** (`k_vec_type_supported = F32‖F16‖Q4_0‖Q8_0`). We were F32.

**The 3 levers** (ranked): (1) f16/q8 KV cache, (2) subgroup-reduction split-KV decode attention, (3) MMVQ int8 GEMV decode matmul.

**Why our split-KV "failed" (~12% slower, [[reference_webgpu-prefill-fix-llamacpp]])**: the technique isn't bad — my impl was incomplete. llama.cpp pairs split-KV WITH subgroupAdd + a cheap reduce pass; I split but used manual cross-WG reductions whose overhead ate the occupancy gain. Per the self-criticism mandate: replicate flash_attn_vec faithfully (subgroups) before judging.

**f16 KV cache TRIED + REVERTED — caused 12× decode regression** (shipped 5c24f1a, reverted 960660e, 2026-06-22). A/B in ONE preview session on the real Iris Xe (`navigator.gpu` adapter = intel gen-12lp; preview at localhost:8137 IS the real iGPU, NOT software): f32 KV = **25.3 tok/s**, f16 KV = **2.0 tok/s**. GPU-timestamp profiling (E.beginProfile/endProfile, aggregate by label) found the cause (NOT thermal — user explicitly forbade that excuse):
1. **f16 attention is SLOWER not faster** (attnDecode 17→22ms at S=1030): decode attn is latency/ILP-bound (correctly predicted), so halving bytes doesn't help AND the `vec4<f32>(K[...])` conversion adds ops to the ILP-bound inner dot loop.
2. **The 56 `castCopyF16` compute passes (2/layer) stall the tiled iGPU**: f32 writes KV via cheap `copyBuffer` transfers; replacing them with tiny compute passes (write→read barrier each) added ~388ms inter-pass GPU bubbles/token (gpu_drain 35ms→430ms vs 42ms actual compute; readback map_ms 1ms→33ms = GPU left downclocked).

**GQA-sharing TESTED + REJECTED — 0.934× (7% SLOWER), 2026-06-23, not shipped.** Implemented a real GQA-shared decode kernel (1 workgroup per KV head, reads each K/V row ONCE + computes BOTH grp=2 query-heads via register reuse; subgroup-coalesced scores + 2 per-head shared-mem softmaxes; S≤3072 cap else fall back to per-head). CORRECT (self-test 1.27e-7). Reliable A/B = GQA + per-head INTERLEAVED in ONE beginProfile batch (identical clock); the sequential-toggle _benchAttn A/B is GARBAGE (gave +18% one run, −28% the next, pure clock drift). WHY slower: the **L2 cache already absorbs the GQA-redundant reads** (grp's 2 q-heads run close in time → cache serves the 2nd), so halving LOGICAL reads doesn't cut DRAM traffic, while half-occupancy (8 WGs vs 16) + doubled score/softmax compute cost more. **This is why llama.cpp WebGPU flash_attn_vec does NOT GQA-share** (one q-head/WG, banks on cache, parallelism from KV-split). LESSON: trust the llama.cpp design signal; ALWAYS A/B kernels interleaved-in-one-batch with GPU timestamps. Net: coalesce + KV-split + f16-KV + GQA-share ALL neutral-or-worse → decode attention is at the iGPU's practical limit; matmuls (DP4A, shipped) were the only real decode lever.

**Coalesced subgroup decode attention TRIED → NEUTRAL (2026-06-22, not shipped).** Rewrote ATTN_DEC_WGSL score loop: each subgroup owns keys {sgid,sgid+nsg,...}, lanes split head dims (coalesced K reads) + barrier-free subgroupAdd (uniform niter loop to keep subgroupAdd in workgroup-uniform control flow). Correct (self-test 1.3e-7). Clean same-session A/B (clock-normalized via matvec ref): baseline norm 0.0437 vs subgroup 0.0410 — within noise. WHY neutral: decode attention is ALREADY bandwidth-bound near peak — at S=2790 baseline does 45.7MB in 1.14ms = ~40 GB/s ≈ 80% of this iGPU's mem BW. It was never coalescing-limited. **So the ONLY way to speed decode attention = MOVE FEWER BYTES: GQA-sharing (each KV head read twice today, once per q-head in its grp=2 group → read once ≈ halve KV traffic) or quantized KV (f16 slow on Intel path; q8_0 untested). Matmuls (gemvQ+gateupQ ≈45% of decode) have headroom via DP4A int8 MMVQ — not BW-bound.** Decode forward @S=1030 = 35.85ms GPU: attnDecode 17 (47%), gemvQ 11.5, gateupQ 4.6.

**GQA-sharing decode TRIED → 2× SLOWER (2026-06-22, not shipped).** Flash/online-softmax kernel, ONE workgroup per KV head processing all grp(=2) query heads, K/V tiles loaded to shared ONCE per tile and reused across the group → halves KV DRAM traffic. CORRECT (self-test 1.8e-7). But clean A/B: normalized 0.082 vs baseline 0.0437 = 2× SLOWER. Mechanism: flash-tiling (needed to fit grp-query state in 32KB shared without storing full S scores) creates ~700 workgroup barriers/call (4 barriers × S/KT tiles, KT=16) ≈ ~2ms of pure barrier overhead at ~3µs/barrier — swamps the halved DRAM; plus occupancy drops 16→8 WGs. Can't fix with bigger KT (KT large enough to cut barriers needs >100KB shared; budget 32KB). Non-tiled GQA-share also blocked (2× f32 score storage + grp PV partials exceed 32KB). **VERDICT: decode attention is near-optimal as the simple non-tiled per-q-head kernel — it's bandwidth-bound near peak (~40 GB/s) with minimal barriers; EVERY byte-reduction restructure (f16, coalesce/subgroup, GQA-tile) adds more overhead (barriers/occupancy/conversion) than it saves on this small iGPU. Stop optimizing decode attention.** Remaining decode lever = the matmuls (gemvQ 11.5ms + gateupQ 4.6ms ≈ 45% of the 35.85ms decode forward @S=1030); gemvQ runs ~19 GB/s reading int4 weights (vs 40 peak) so it has headroom, but DP4A int8 is NOT the lever (int4 weights are already smaller than int8) — the lever would be int4 GEMV access/dequant efficiency. Unverified.

**GQA-sharing decode attention TRIED → 9% SLOWER (2026-06-23, not shipped).** New kernel ATTN_DEC2_WGSL: one WG per KV head (8 WGs), processes BOTH grp=2 query heads, reads K (scores) + V (PV) ONCE reused for both → halves KV DRAM. f16 score buffers (sc0/sc1) to fit 2×MAXS in 32KB shared. Correct (self-test 3.4e-4, f16-P precision). Same-session interleaved warm A/B (6 reps each, median): base per-head 1.88ms vs GQA 2.07ms = **0.91× (slower)**. WHY: decode attention is NOT bandwidth-bound (base ~23 GB/s ≈ 46% peak when carefully measured warm — earlier "80%/40 GB/s" was a high-clock fluke) → it's compute/occupancy/latency-bound. GQA's halved WG count (8 vs 16 → less latency hiding) + doubled per-WG work (2× softmax reductions + 2× exp + 2× PV) outweigh the halved reads. **CONCLUSION: decode attention is at this iGPU's practical limit. FOUR approaches now tried, all neutral-or-worse: coalesced-subgroup (neutral), split-KV (neutral/slower), f16 KV (12× worse), GQA-share (9% slower). The plain per-head ATTN_DEC_WGSL (cd6670c) is the keeper. Stop optimizing decode attention.** Remaining decode lever = the MATMULS (gemvQ+gateupQ ≈45% of decode).

**DP4A int8 GEMV SHIPPED (commit 3c30e42, ?v=66) — 1.21× on the converted matmuls (~6% decode), the FIRST real decode win of the saga.** GPU-timestamp bench (the per-dispatch wall-clock bench was useless — submit overhead dominated; must batch in beginBatch/endBatch + beginProfile): gemvQ runs ~20-28 GB/s + ~70-100 GFLOP/s = neither saturated → COMPUTE-limited by f32 dequant+dot, not bandwidth → DP4A helps. Impl: QUANTQ8 kernel quantizes activation→per-group(32) int8 (one workgroup/group, parallel abs-max + pack4xI8; the naive 1-thread/group version was 17-34us pure occupancy overhead → fixed to 4-9us) + GEMVDP4 kernel (weights stay int4 same-bytes, unpack nibbles→repack int8 in-shader, two f32 dot4 → two dot4I8Packed ~4× less ALU, int32 accum × wscale × xscale). Net 1.0-1.25× per shape (biggest on wide N; lm_head 1.18×). Correctness: self-test gemvDP4A 0.27% rel, 40-tok generation BYTE-IDENTICAL to f32 (int8 act error doesn't move greedy, like llama.cpp MMVQ). `pack4xI8`+`dot4I8Packed` both compile on this Dawn/gen-12lp. linearQ T=1 → gemvDP4A by default; `globalThis.__noDp4=true` forces f32 gemvQ fallback (used for A/B). **gate+up DP4A SHIPPED (commit 04c5d7d) but MARGINAL (~1.05× median, noisy 0.96-1.35; vs gemv's clean 1.21×).** GATEUPDP4_WGSL: quantize activation once, dot4I8Packed vs both gate+up weights. Correct (self-test 0.24% rel). Net-positive median (kept; unlike GQA which was median-NEGATIVE 0.93× and rejected), but small because gate+up reads 2× the int4 weight bytes (gate AND up) → closer to bandwidth-bound, plus 2× the pack4xI8 overhead → less DP4A (compute) benefit. Same __noDp4 toggle gates all DP4A.
**REMAINING FOLLOW-UP: quantize the activation ONCE per layer and reuse across q/k/v/gate/up — they all read `normed`, currently each gemvDP4A re-quantizes it (~5 redundant QUANTQ8/layer ≈ 0.5ms).** o_proj/down read different activations (attn/swi) so need their own quantize.

**TESTING DISCIPLINE (cost hours this session — phantom "decode bug"):** TWO cache layers make iterative kernel tests serve STALE code → identical wrong results across edits: (1) the **service worker** (sandpie.js, registered in conversations.js) intercepts module fetches; (2) the **engine pipeline cache** (`getPipeline` keys by label e.g. 'q3.attnDecode' and IGNORES the wgsl arg — so eval-reload-same-engine reuses the first-compiled kernel). To test a kernel edit RELIABLY: edit file → bump sandpie.html ?v= → in page: unregister SW + `caches.delete` all → `location.reload()` (fresh engine = fresh pipeline cache) → then run selfTestKernels. `eval(fetchedSource)` does NOT work (engine pipeline cache persists). Preview localhost:8137 adapter IS the real Iris Xe (gen-12lp). A no-op/failed-compile dispatch leaves O zero → self-test err 0.069 (== "kernel didn't run").

**LESSON**: f16 KV is NOT a standalone lever on our f32 ILP kernel — it only pays off as part of llama.cpp's subgroup `flash_attn_vec` package (DIRECT f16 writes from rope/v_proj, no separate cast pass, + subgroup reductions). Per the self-criticism mandate (llama.cpp uses f16 KV → assume MY impl failed): the cast-pass + bolt-on-to-f32-kernel WAS the failure. Don't re-add f16 KV until doing lever #2 (subgroup split-KV decode attention) and folding f16 writes into it. **Methodology that worked**: same-session A/B (revert engine file via `git checkout cd6670c -- `, bump ?v= to cache-bust, reload) + per-kernel GPU timestamps + _PERF (encode/gpu_drain/map split) — this is how you isolate a regression.
