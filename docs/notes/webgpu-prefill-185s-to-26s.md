# webgpu-prefill-fix-llamacpp

> WebGPU engine prefill is catastrophically slow + crashes the iGPU; root causes + fix plan ported from llama.cpp ggml-webgpu

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

Dense Qwen3 WebGPU prefill (modules/webgpu-qwen3.js, the stale c9fdbdf-derived file) MEASURED on the i5-1235U Iris Xe gen-12lp (2026-06-22): prefill is **GPU-execution-bound** (T=2790: wall 205s, encode 1.8s, gpu_drain 203s — NOT CPU/main-thread, NOT the page/Pyodide; same slowness in sandpie AND web-engine-test.html harness → it's the ENGINE). Cost is super-linear: T=128→1.8s, 256→3.9s, 512→9.4s, 2790→185s (fits ~13·T + 0.01·T²). decode is fine (~5 t/s under app render contention). **A full-prompt single forward = one queue.submit ~185s → Windows GPU watchdog TDR → driver reset → WHOLE-PC FREEZE (user reproduced 2026-06-22).**

Two root causes (confirmed by reading the kernels):
1. **matvecQ is GEMV-style**: linearQ loops ceil(T/MATVEC_MAXT) tiles, RE-READING the full int4 weight matrix from VRAM each tile → weight traffic ∝ T (dominant at moderate T). MATVEC_MAXT raise 16→32 didn't help (still re-reads).
2. **attention is O(T²)**: ATTN_WGSL dispatches one workgroup per (token,head), each serial-loops over ALL S keys (dominant at large T).

**Reference = llama.cpp ggml-webgpu** (github.com/ggml-org/llama.cpp, ggml/src/ggml-webgpu/; PR #17031 "faster matmul"). Shaders copied to this session's scratchpad (reg_tile.wgsl, decls.tmpl, subgroup.wgsl, flash.wgsl, quant.tmpl, backend.cpp). What they do that we don't:
- **mul_mat_reg_tile.wgsl** = real 2D GEMM (M=tokens) when ne[1]>1: BOTH operands staged into shared mem ONCE per K-tile, register-tiled (TILE_M×TILE_N, f32 accum, f16 operands), each weight read from VRAM once per output tile, reused across all tokens. GEMV path used ONLY when ne[1]==1 (decode). ← the 10× lever.
- **dequant-once-into-shmem** (mul_mat_decls.tmpl init_shmem_src0 + quant_inner_loops.tmpl): int4→f16 into shmem once per K-tile, reused — no per-token dequant. Same GEMM kernel for quant+f16.
- **flash attention** (flash_attn.wgsl subgroup-matrix; **flash_attn_tile.wgsl = subgroups-no-matrix = the Iris Xe path**; flash_attn_vec_* decode): tiled, online softmax, KV streamed in blocks; scores never materialized; NO O(T²) serial loop.
- **bounded submits**: WEBGPU_DEFAULT_COMMAND_SUBMIT_BATCH_SIZE=64 kernels/submit + max_inflight throttle (WaitAny drain) → never one giant submit → no TDR. (compute_2d_workgroups also folds dispatch under the 65535/dim limit.)

FIX PLAN — ALL SHIPPED (2026-06-22), prefill 185s → **26s (7.1×)** on gen-12lp (?v=57), output token stable (tok=1540), crash-safe. (Stages: 185→48s via GEMM+flash+chunking+submit-split, then 48→26s via vec4 attention.):
1. chunked prefill (a31aa9b ?v52) then chunk=256 (1efef96 ?v56): _streamIds processes the prompt in PREFILL_CHUNK-token blocks; correctness via global posBase+t (RoPE/KV-offset/attn-mask), KV accumulates across chunks.
2. tiled int4 GEMM gemmQ (fda7b7c ?v53, BM tuned a120897): port of reg_tile — weight tile dequant→shmem ONCE per K-tile, reused across BM tokens; replaces matvecQ's per-tile re-read. GEMM_BM=128 (BM=256 = 512-thread WG + 16KB shmem HURT Iris Xe occupancy: 10.95ms vs 6.6ms); gemmQ T=256 fills 2 M-blocks "free" so chunk=256 halves matmul wall. linearQ: T==1→gemvQ (decode), T>1→gemmQ. Bench 2-3.5× vs matvecQ.
3. tiled FLASH attention (c305d40 ?v55): online softmax, 1 workgroup per head×QT(16)-query block, K/V streamed in KT(8) tiles to shmem reused across queries (~16× fewer KV reads). + causal early-exit skip masked key-tiles (1efef96). Replaced the old 1-workgroup-per-(query,head) kernel whose T queries EACH re-streamed full KV (9.7s for ONE 128-tok chunk at S=2790).
4. engine submit-splitting (webgpu-engine.js _batchTick, 1efef96 ?engine-v43): flush batch encoder every 32 GPU ops so no single submit trips the OS GPU watchdog (TDR) regardless of chunk size; correctness-neutral; mirrors llama.cpp COMMAND_SUBMIT_BATCH_SIZE=64. Unblocks bigger chunks.

REMAINING: attention is now ~80% of GPU (~38s of 48s, ~183ms/layer at T=256,S=2790). It's REUSE-bound: KV re-read T/QT times per head, QT capped ~16 by shared-mem acc[QT*hd]. FOUR optimizations TRIED + REVERTED, none improved (2026-06-22): (1) KT/QT swap 8/16 → 189ms worse; (2) f16 Q/K/V in shared → 333ms worse (f16 shared access overhead on Intel); (3) +1 bank-conflict padding → 183ms no change (not bank-bound); (4) **register-tiled acc (one-thread-per-query, QT=32, acc[hd] in private array) → 1143ms, 6× WORSE: WGSL/Tint on Intel SPILLS large dynamically-indexed private arrays to scratch memory (NOT registers) — the classic WGSL register-tiling pitfall. Do NOT retry naive register-acc.** **CORRECTION (the "48s is near the limit / attention is reuse-bound" conclusion was WRONG — it was ILP-bound).** Rigorous regime profiling: baseline attention = 33 GFLOP/s = 27% of the GPU's 124 GFLOP/s GEMM peak, only 4 GB/s → LATENCY/ILP-bound, NOT bandwidth- or reuse-bound. Cause: score dot was a single serial f32 accumulator over hd=128 (each add waits on the last), no ILP. **FIX (302155e ?v=57): vec4 the attention — Q/K/V/O read as vec4, score accumulates into a vec4 (4 independent lanes) + 4× fewer iters, acc/V-accum vectorized too. Self-test 8e-7, _benchAttn S=2790 177.8ms→52.8ms (3.4×), now 111 GFLOP/s ≈ 90% of peak. End-to-end prefill 48s→26s.** METHODOLOGY LESSON (per user): isolate ONE feature, PROFILE to find the regime, then act — don't guess. The earlier 4 "failed" attempts mis-measured (KT/QT noise; f16-shared real but unexplained; padding null; register-acc was a CONFOUNDED multi-variable change wrongly blamed on scratch-spill). The real lever (ILP/vec4) was reachable WITHOUT leaving the shared-acc/WG=128 structure — register-acc was the wrong abstraction. Matmul gemmQ is now ~comparable to attention (~10s each of the 26s). PROFILED 2026-06-22: at T=256 (the chunk size) gemmQ = 200-235 GFLOP/s = ~1.6-2× the f32 GEMM peak (124), and GFLOP/s plateaus with T → COMPUTE-BOUND/saturated (int4 8× fewer bytes + 4×4 register tile already deliver). Only dip is T=64 (occupancy, irrelevant at chunk=256). **Verdict: gemmQ is near its ceiling, DO NOT optimize — no headroom, vec4/more-tiling would be churn or regress (cf BM=256).** Untried: f16 KV (bandwidth — but attention is compute-bound now at 90% peak, so won't help).

LOAD-TIME fixes (the ~45s before first inference): (1) tokenizer.json ~11MB cold fetch from HF ~20s (plain git file, slow backend not LFS CDN) — overlap with weight download (9b3ad1b) + persistent Cache API (5bbc541). (2) **THE BIG ONE — cache the QUANTIZED int4 result, not the f16 safetensors (cfc9974 ?v=63): every load was re-reading 1.5GB f16 + re-quantizing to int4 in JS (~45s). Now loadModel serializes int4 pack/scales+f16-embed to one ~647MB blob and stores it chunked in the Cache API; warm loads read chunks→GPU, no download/quantize. Verified: cold 89.5s→warm 6.2s, token identical (547).** GOTCHA: **Chrome Cache API rejects single entries >~200MB ("Unexpected internal error")** — measured 192MB OK / 256MB FAIL on gen-12lp (≈quota-relative); this is why the old 1.5GB safetensors cache.put silently failed (model never cached) → MUST chunk large blobs (used 64MB chunks + manifest). Engine now runs in a Web Worker (0ae7b8f: webgpu-worker.js + webgpu-host.js, importScripts webgpu-engine.js+webgpu-qwen3.js) so load+inference are OFF the main thread; Cache API works in workers. sandpie.html ALSO loads webgpu-qwen3.js main-thread (for DEFAULT_MODELS/selfTest/harness). Remaining warm-load 6.2s = read 647MB cache + concat + GPU upload (could parallelize chunk reads / skip concat, diminishing).

DECODE (T=1) fix (cd6670c ?v=58): long-context decode was slow + "GPU at 30%" because the PREFILL flash kernel (QT=16 query block) at T=1 wastes ~15/16 work (15 invalid query slots, ~8/128 threads in score) → 5 GFLOP/s, ~120ms/tok attn at S=2790, and low occupancy kept the iGPU DOWNCLOCKED (jitter). Fix = dedicated single-query kernel (llama.cpp flash_attn_vec analogue): route T==1 to ATTN_DEC_WGSL — ONE workgroup/head, 128 threads split keys (vec4 dot + parallel max/sum reduce), 128-thread PV (nd dims × ng key-groups, reduced); query attends all keys (no mask). selfTest attentionDecode 1.9e-7. _benchAttn T=1 S=2790 4.28→1.78ms (2.4×). **END-TO-END decode @2700-tok context: ~2-6 tok/s (jittery) → 25.5 tok/s (4-10×, stable)** — compounding: higher occupancy → iGPU boosts clock instead of idling. Still occupancy-limited (16 WG/head, ~13 GFLOP/s); split-KV (G workgroups/head + combine pass) would fill the GPU further if needed, but 25 tok/s is usable. In-app decode delivered only ~12.7 tok/s vs ~25 pure-GPU because the engine ran INLINE on the main thread competing with per-token rendering.

DP4A int8 GEMM is now the DEFAULT prefill matmul (2026-06-25, commit d8db4ed, ?qwen3 import v=90 worker / webgpu-worker.js v=7 / webgpu-host.js v=8 / harness v=90). This SUPERSEDES the "gemmQ is near its ceiling, DON'T optimize" verdict above — that verdict was right about the *f16* gemmQ kernel (it IS ~2× f32 peak, compute-bound), but the win came from a DIFFERENT kernel: gen-12lp has no XMX/tensor cores, so its native fast matmul path is `dot4I8Packed` (DP4A) — the SAME instruction llama.cpp's coopmat lowers to on this GPU. `linearQ` T>1 now routes to `gemmDP4A` (codegen-unrolled int8 DP4A GEMM, `gemmdp4Wgsl`, 64×64/BK=32/TM=TN=4 static scalar accumulators — the array<>-spill→unroll lesson again, same as the f16 GEMM fix); `globalThis.__noDp4Gemm` forces the old f16 gemmQ. The first DP4A attempt LOST (0.58×) purely from `array<>` accumulator spill, and a noisy reps=14 ratio bench once showed gate/up at 0.95× — both were measurement/impl artifacts, NOT a hardware wall. RELIABLE method = new `_benchGemmTS` export: GPU-timestamp, min-of-reps (wall-clock swings ±50% on this throttling iGPU; min-time = the unthrottled floor; it also separates the activation-quantize, label /quant/, which is <2% of the GEMM). Two independent reps=20 passes, T=256, f16→DP4A GFLOP/s: gate/up 6144×2048 317→396 & 318→376 (1.18–1.25×); down 2048×6144 294→420 & 316→395 (1.25–1.43×); q/o 2048×2048 414→508 & 312→436 (1.23–1.40×); k/v 1024×2048 295→394 & 368→537 (1.34–1.46×). Absolute numbers wobble ~10% under throttling but DP4A wins EVERY shape EVERY run by 1.2–1.45×. relErr ~1% (int8 activation quant) — safe because decode already runs the identical int8 DP4A path (gemvDP4A) coherently. The old array<>-based GEMMDP4_WGSL const (~lines 774-860) is now dead/unused (left in place). END-TO-END coherence with DP4A prefill NOT yet runtime-verified (preview keeps navigating off the harness + evicting the 1.1GB quant cache → model loads are flaky); rests on relErr ~1% + the shared int8 decode path. DECODE-COLLAPSE in the worker (2026-06-22): symptom = GPU 100% during prefill then drops to ~16% (STARVED, not saturated) + jank + ~2 tok/s mid-decode. The dedicated decode kernel (cd6670c) is INTACT (verified) — not a regression. Cause = the worker thread can't feed the GPU because the few-core CPU is starved. TWO fixes: (1) **adaptive paint cadence (f05f59c ?conversations v=26)** — RoundRenderer._paintContent re-parsed the WHOLE message (marked+DOMPurify) every 16ms = O(len)/frame; once a paint exceeds the frame budget the drain loop pins the main-thread CPU → starves the worker → GPU idles. DECODE-COLLAPSE — REAL CAUSE (2859262, supersedes the render-throttle/worker theories below which were WRONG: user's CPU was 10%, GPU 16% — both IDLE, not contended; external providers were fast → renderer fine). MEASURED: decode used submitOnly CHAINED forwards (GEN_BATCH queued, no per-forward CPU drain, one batched readback). On the Intel iGPU this left the GPU DOWNCLOCKED — with no CPU awaiting GPU completion, the power governor parks the clock at minimum and every forward ran ~155ms (~5 tok/s). Proof: isolated DRAINED forward (await each) = 15-19ms GPU / ~25ms wall (~40 tok/s) vs 155ms chained; GEN_BATCH size irrelevant (per-batch gap scaled with batch → per-forward bound, not per-readback). FIX = one DRAINED forward per token (forward(null,pos,{chain:true}) drains + returns the token; no submitOnly, no batched readU32Range) in BOTH generate() + _streamIds. Worker end-to-end 4.4→22.7 tok/s (median 38ms/tok). The old "25 tok/s @v=58" was gpu_drain_ms only — it MASKED the wall stall. LESSON: submitOnly/pipelining is a dGPU optimization that BACKFIRES on iGPU power management — the CPU-wait is what boosts the clock. The Web Worker (0ae7b8f) and adaptive-paint throttle (f05f59c) were both built on the wrong render-contention diagnosis; the worker is harmless (decode fix works in it, 22.7 tok/s) but wasn't the cure.

SPLIT-KV decode attention (flash-decoding) — TRIED + PROFILED + REJECTED 2026-06-22 (was NOT shipped). Implemented as 2 passes (partial m/l/Σp·V per KV chunk over SPLIT_G=8 workgroups/head + a combine pass), self-test correct (2.2e-7). Per-kernel GPU-timestamp profiling of ONE decode forward at S=2640 (toggled via _setDecMode): attention = 66% of the forward (42ms of 64ms single-WG). CLOCK-NORMALIZED (gemvQ is identical work in both modes but read 13.8ms single vs 11.2ms split → the split run's GPU was ~1.23× higher-clocked from running 2nd): split attention = 38.4×1.23 = 47ms vs 42ms single → split is ~12% SLOWER at equal clock. The end-to-end "neutral" earlier was real (clock drift masked a small regression). WHY split-KV doesn't help on THIS hardware (it's standard on dGPUs): production engines target dGPUs with 100s of SMs where 16 WG badly underutilize → split's occupancy gain is huge; the Iris Xe has ~96 EUs and 16 WG × 128 threads ≈ 2048 in-flight already occupies it, AND the attention runs ~1 GB/s (far below ~50 GB/s) → it's LATENCY/access-pattern bound, not workgroup-count bound, so more workgroups just add 2-pass+combine+partials-I/O overhead. DON'T re-add split-KV on iGPU. The decode attention bottleneck (KV scan ∝ S) is inherent; inline decode at cd6670c is healthy (~15-20 tok/s @2640, warm GPU). main stays at cd6670c.
