# reference_bitnet-cpp-windows-build

> How Microsoft bitnet.cpp builds + runs on the i5-1235U Windows box; BitNet 2B4T i2_s works + chats but is slow (~3.5 t/s) — TL2 is the fast x86 path

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

Built Microsoft **bitnet.cpp** on the daily i5-1235U laptop 2026-06-16. Repo at `C:\Users\aezequiel\bitnet` (venv `.venv`; model staged at `models\BitNet-b1.58-2B-4T\ggml-model-i2_s.gguf`). Toolchain: **VS Build Tools 2022 + Clang + Win11 SDK** (winget `Microsoft.VisualStudio.2022.BuildTools` with VCTools + VC.Llvm.Clang + Windows11SDK; uses ClangCL). Build = `Enter-VsDevShell` then `python setup_env.py --model-dir models/BitNet-b1.58-2B-4T -q i2_s` (NO `--hf-repo` → reuses the official i2_s GGUF, **skips torch/convert + 5 GB download**).

**Two source patches needed — the pinned old llama.cpp fork won't compile under the newer Clang:**
- `src/ggml-bitnet-mad.cpp:811` → make it `const int8_t * y_col = y + col * by;` (clang rejects dropping const).
- add `#include <chrono>` to BOTH `3rdparty/llama.cpp/common/common.cpp` and `common/log.cpp` (use `std::chrono::system_clock` without the include).
Build `--target llama-cli` only — skips example binaries that have their own clang nits.

**Result:** BitNet 2B4T (arch `bitnet-b1.58`, 1.10 GiB i2_s) loads + chats coherently (real instruct, far better than TriLM base). **BUT gen ≈ 3.45 t/s** on this chip (i2_s + AVX2, no AVX-VNNI) — *slower* than mainline TQ2_0 TriLM-3.9B (24.7) and Qwen2B-Q4 (~13.5, see [[reference_llamacpp-bench-i5-1235u]]). **i2_s = compatible-but-slow; the fast bitnet.cpp x86 kernel is TL2** (`-q tl2`), which requires converting from HF safetensors (torch + ~5 GB) — the path we skipped. So on x86 the bitnet.cpp speedup needs TL2; i2_s alone doesn't deliver it. Chat via `llama-cli ... -cnv`; launcher `C:\Users\aezequiel\bitnet\chat-bitnet.ps1`. Cousin facts: [[reference_bonsai-8b-eval]] (other fork-only ternary), [[reference_wllama-webgpu-crash]] (mainline needs TQ2_0 not I2_S).

**TL2 0xC0000005 — investigated 2026-06-16; STACK-OVERFLOW HYPOTHESIS TESTED & REFUTED.** Plausible lead: generated kernel stack-allocates `alignas(32) uint32_t CBits[BATCH_SIZE*BM]` (`include/bitnet-lut-kernels.h:480`, ≤640 KB at bs=512) on ggml worker threads that Windows gives a **1 MB** stack (`ggml.c:150` `CreateThread(NULL,0,…)`; Linux pthread=8 MB). FIX APPLIED (CreateThread → 8 MB via `STACK_SIZE_PARAM_IS_A_RESERVATION`) + rebuilt + converted `1bitLLM/bitnet_b1_58-3B` → TL2 (0.83 GB, 2.13 BPW) — **STILL CRASHES.** Minimal repro `llama-cli -t 1 -n 8 -p Hello` (single-thread, bs=1, 8 MB stack) → **0xC0000005 (-1073741819) at the FIRST forward pass** (`common_init_from_params: warming up the model`). So NOT a stack overflow / NOT threading / NOT batch size — it's a genuine bug in the TL2 LUT compute kernel as built by **Clang 19.1.5 on Windows** (model loads fine; i2_s runs fine; only TL2 faults → smells like a miscompile/UB the maintainers' older-clang/Linux toolchain doesn't hit). Windows fix UNKNOWN: would need WinDbg on the faulting instr, or try rebuilding `src/ggml-bitnet-lut.cpp` at lower opt (`-O1`/`-fno-strict-aliasing`). **WSL/Linux is the realistic path to TL2 speed.** Latent bonus bug stands: setup_env codegens 2B4T's TL2 with bitnet_b1_58-3B dims (3200/8640 ≠ 2560/6912). NET on this box: ternary that WORKS = i2_s 2B4T (3.45 t/s, instruct) + mainline TQ2_0 TriLM-3.9B (24.7 t/s, base); TL2 LUT speed not reachable on Windows without a kernel/compiler fix.
