# litert-mldrift-gpu-techniques

> What makes Google LiteRT-LM's in-browser GPU inference fast (MLDrift runtime) and which techniques are portable to our WebGPU Qwen engine

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

LiteRT-LM web (`@litert-lm/core`, jsdelivr/unpkg) = thin JS wrapper over **MLDrift**, Google's GPU ML runtime compiled to wasm. The 18.9MB file is `wasm/litertlm_wasm_internal.wasm` (the listing swaps the .js/.wasm sizes; the .js is the 291KB Emscripten MODULARIZE wrapper). Kernels are authored in a C++ tensor DSL (`mpp::tensor_ops` / "UCL") and **transpiled to WGSL at load time** from templates (`@compute @workgroup_size(WORKGROUP_SIZE_X,...) fn main`). No static WGSL library to lift — but the recipe is fully visible in the wasm strings (extract printable runs ≥10 chars and grep). It's the classic TFLite-GPU mobile recipe.

**Four pillars (none of which our engine [[sandpie-webgpu-engine]] used as of v73):**
1. **f16 compute + storage** — `enable f16`, `threadgroup half a_loc[]`, `half4` reads everywhere. Halves memory bandwidth = dominant cost on mobile; Adreno is native-f16. We forced **f32 everywhere** for "mobile safety". 🔴 biggest miss.
2. **Subgroup-matrix (cooperative matrix) GEMM** — `subgroupMatrixMultiplyAccumulate`, `subgroupMatrixLoad`, `#extension GL_KHR_cooperative_matrix : require`, `mpp::tensor_ops::matmul2d<desc, execution_simdgroups<SIMDGROUPS>>` with `get_destination_cooperative_tensor`, tiled M_TILE/N_TILE/K_TILE. Hardware matrix units = the prefill lever. Gated on Chromium-experimental subgroup-matrix (very new, desktop-first; probably NOT on Android Chrome yet — probe, don't assume). We have NO subgroup-matrix (~129 GFLOP/s portable tiled f32 on Iris Xe).
3. **Texture-backed tensors** — `image2d/image3d/image2d_array`, `.Read(w,h,slice)`, 4-channel depth-slicing (`Slices()`), `TensorStorageType` BUFFER/IMAGE_BUFFER/TEXTURE_2D/TEXTURE_ARRAY chosen per device. Adreno/Mali texture caches beat storage-buffer loads. Biggest rewrite. We use storage buffers.
4. **int4 folded-bias dequant** — per-group f16 scale+zero (`half4 w_scale/w_zero_point = args.weights_scale.Read(...)`), folds the offset: `half4 w_bias = -w_scale*8.0h + w_zero_point` (dequant = one FMA); `ucl::U32x2ToU4x16AsVec4x4<half>` unpacks u32x2→16 int4 as 4×half4; weights cached in threadgroup mem as half4. Cheap micro-opt we can copy directly (we do int4 group-32 but f32 dequant, no folded bias).

Also: shared-mem two-accumulator RMSNorm (sum + sum-of-squares in one pass), vec4 reductions, XNNPACK present for some CPU ops.

CORRECTION (learned while porting): our engine was NOT "f32 everywhere" — it already declares `enable f16` in nearly every kernel, stores weights/scales as f16, and gemmQ already stages shared tiles as vec4<f16>. The real gap was that gemmQ's inner dot CONVERTED f16→f32 and multiplied in f32 (f16 was storage-only). gemvQ (decode) is still fully f32.

**EMPIRICAL CAPTURE (2026-06-27, the ground truth — supersedes the wasm-string guesses above):** hooked `GPUDevice.prototype.createShaderModule` on the MAIN thread (LiteRT runs main-thread) and dumped all **190 WGSL shaders** MLDrift compiled for a real Gemma-4-E2B prefill on Iris Xe gen-12lp, with our shipped **fp32-forced device** (litertlm.js deliberately omits the `shader-f16` feature). Result: **NO `enable f16` / f16 math, NO subgroups, NO subgroup-matrix, NO dot4I8Packed/DP4A in ANY of the 190.** The four-pillars list above describes templates that EXIST in the wasm but are only emitted when the device exposes those features (shader-f16 / experimental subgroup-matrix) — on our fp32-forced device MLDrift falls back to **f32 compute**. So for OUR shipped config the prefill edge is NOT f16-math or matrix units; it is: **(1) texture-backed tensors with `rgba16float` storage** — 140/190 shaders; activations/intermediates in f16 TEXTURES (half bandwidth + texture cache, 2D locality), compute read back to f32 (no shader-f16 needed — `pack/unpack2x16float` is core WGSL); **(2) 8×4 register tiling** (8 tokens × 4 out-channels = 32 f32 accumulators, vec4 `dot()`, split-K across 8 threads + workgroup tree-reduce); **(3) fused epilogues** (mask/bias/store in the matmul dispatch); **(4) int8 ASYMMETRIC weights** (zp=128, 16-per-vec4<u32>, per-channel f16 scale via Unpack4x16float, dequant inline). Full kernel #142 saved at scratchpad/mldrift-matmul-kernel.wgsl. So our gemmQ's compute (vec4 dot, register tile) is already close; the gap is DATA MOVEMENT (flat f32/int8 storage buffers vs f16 textures + cache). Texture port = near-total rewrite of webgpu-engine.js tensor layer + every kernel; ~1.5× prefill (269→411 tok/s), does NOTHING for reliability. Cheaper partial: f16 ACTIVATION storage (pack2x16float in storage buffers) + fused epilogues, lower risk. Strategic note: this capture is the strongest case FOR adopting MLDrift's runtime via a MediaPipe `.task` loader instead of reimplementing it. See [[reference_litert-web-qwen-unsupported]] (web SDK can't load Qwen — Gemma only).

**TEXTURE GEMM RESOLVED on Intel gen-12lp (2026-06-27, RIGOROUS — captured MLDrift's REAL bulk kernel + faithful port). Conclusion: textures are NEUTRAL (not slow, not a speedup); our gemmDP4A is already MLDrift-class.** Method matters — earlier slow results were MY bad kernels, NOT textures:
- Re-captured MLDrift on a REAL ~1200-token prefill, hooking `createComputePipeline` (override constants) + dispatch. The bulk prefill matmul (shaders #15/23/52/56/73… repeated per layer) is **`@workgroup_size(64,1,1)`, NO split-K**, and **STAGES f16 weights in workgroup memory** (`var<workgroup> weights_cache: array<vec4,32>`, cooperatively loaded via Unpack4x16float, reused across the 64 threads). Each thread = 1 token × 32 output channels (8 vec4 accumulators); activation read from a texture (1 vec4/token/K-step, read once). Kernel #142 (8 hardcoded tokens, split-K, workgroup reduction) that I first analyzed is the SMALL-BATCH/decode kernel, NOT bulk prefill — my gemmTex2 wrongly copied it.
- `gemmTex3` = FAITHFUL port (SLM-staged f16 weights + texture activations, 64-thread, no split-K) → **801 GFLOP/s = EXACTLY gemmDP4A's 801** (4 shapes: 1.00/0.97/0.99/0.92×, correct non-zero output). So a correctly-built texture GEMM MATCHES our buffer GEMM.
- Earlier failures explained: gemmTexQ 78 / gemmTex2 103 GFLOP/s were slow because they had NO shared-mem weight staging (relied on texture cache for everything) + gemmTex2 used split-K from the wrong kernel. NOT because textures/sampler are slow.
TAKEAWAY: MLDrift's prefill speed = standard SHARED-MEM WEIGHT TILING (same principle as gemmDP4A); the texture is just the activation store, neutral on Intel. Our gemmDP4A (~560–800 GFLOP/s by shape) is ALREADY MLDrift-class — no GEMM win available from textures, DON'T rewrite the engine for them. The "MLDrift 1.5× faster prefill" (411 vs 269 tok/s) was a CROSS-MODEL tok/s artifact (Gemma-E2B MatFormer activates fewer effective params/token vs Qwen-0.6B dense), NOT a kernel-efficiency gap — never a GFLOP/s comparison. If chasing Qwen prefill, the lever is ATTENTION not the matmul. PREFILL BREAKDOWN MEASURED (2026-06-27, Qwen3-0.6B, T=2560, GPU-timestamp per-label via beginProfile+forward(ids,0)+endProfile, 565 dispatches, 9.66s GPU = 263 tok/s, GPU-bound not dispatch-bound): **attention `attnFlash` 66.1% (6386ms), matmul gemmDP4v2 29.3% (2831ms), quant 2.5%, swiglu 1%, rope 0.7%, rmsnorm 0.3%, lm_head/embed/argmax ~0%.** So attention DOMINATES (2× the matmul). attnFlash runs ~190 GFLOP/s vs matmul ~800 → 4× kernel headroom in attention, ON TOP of the O(T²) algorithmic cost (Qwen3 does FULL global causal attention on ALL 28 layers; Gemma uses sliding-window/local attention on most layers → sub-quadratic → that's the real reason Gemma prefills faster, a model-arch difference not kernel efficiency). ROOT CAUSE of slow attention FOUND (measured 2026-06-27): attnFlash is COMPUTE-BOUND AT THE iGPU's F32 CEILING. Measured T=S=2560 1-layer causal = 26.85 GFLOP in 204.6ms = **131 GFLOP/s**; this iGPU's f32 portable-GEMM ceiling = **123 GFLOP/s** → attention is AT/above the f32 peak, NOT inefficient. NOT bandwidth-bound (moves ~3.3GB in 204ms = 16 GB/s, vs ~50-60 GB/s peak). The "4× slower than matmul" was apples-to-oranges: matmul is fast because int8 DP4A (~800) / f16 (~593); attention runs F32 (ceiling ~123). So the ONLY lever is PRECISION: compute QKᵀ and PV in f16 (keep softmax max/sum f32 — standard flash mixed precision). Intel gen-12lp f16 ≈ 2× f32 rate → ~2× attention → prefill ~263→~370 tok/s (rest vs Gemma 411 = Gemma's sliding-window attention, unreplicable without retrain). CAVEAT: f16 KV regressed 12× for DECODE (different kernel, latency/ILP-bound at T=1, cast passes stalled) — PREFILL is a different regime. **DONE + SHIPPED (2026-06-28, commit d73e13a): f16 prefill attention = 2.0× the f32 kernel in isolation (212 vs 106 GFLOP/s), +35% end-to-end prefill (263→355 tok/s), attention 66%→51% of prefill, output coherent, relErr ~1e-3.** BUT the win was NOT just "switch to f16" — f16 alone gave only 1.09× (so attention was NOT purely FMA-bound; my f32-ceiling diagnosis was incomplete). Real diagnosis via iteration: (1) f16 alone 1.09×; (2) KT tile sweep — KT32 REGRESSED → occupancy/latency-bound not barrier-bound; (3) +4 independent accumulators in the score dot (break the 32-deep dependency chain) → 1.41×; (4) +f16 running-acc (halves SLM → more resident workgroups) + KT=8 (smallest SLM footprint) → 2.0×. So prefill attention was LATENCY + OCCUPANCY bound, fixed by ILP + SLM reduction, with f16 as the enabler. Kernel = attnF16Wgsl(KT) in webgpu-qwen3.js (QT=16,WG=128, f16 qsh/ksh/vsh/acc, 4-acc ILP score+PV, KT=8); attention() routes T>1 here when caps.hasF16 (f32 ATTN_WGSL fallback, __noAttnF16 to disable); DECODE T=1 untouched. _benchAttnF16(T,S,...) sweeps KT + checks relErr. attnFlash kernel = ATTN_WGSL (QT=16,KT=8,WG=128, Q/K/V/O f32 vec4). forward() exported on window.TabInferQwen3 (harness profiling entry); _benchAttn(T,S,nHq,nKv,hd) times one attention() call. Experiment kernels gemmTexQ/gemmTex2/gemmTex3 + benches _benchGemmTex/Tex2/Tex3 left in-tree (gated, not wired into forward); texture helpers in webgpu-engine.js. Buffer engine tagged engine-buffer-backup.

**Port plan for OUR engine (ranked, ties to the [[webgpu-mobile-device-loss-prefill]] fix — faster prefill = chunks fit under the watchdog AND user waits less):**
1. **f16-dot prefill GEMM — DONE (commit 21059cc, module v74).** gemmQ inner dot now `f32(dot(a,b))` (f16 multiply-add, f32 accumulate across K) → ~2× FMA rate on f16 GPUs. Gated by a load-time numerical probe (`probeF16Gemm`, mirrors `probeSubgroups`, NO user-agent sniffing) that A/Bs f16 vs f32 dot and falls back on mismatch. Verified in-browser on Iris Xe gen-12lp: compiles, rel err 9.0e-4 (threshold 3e-2), keeps f16. `_setF16Math`/`_probeF16Gemm` exported for A/B. NEXT in this lever: f16 the gemvQ decode dot too (bandwidth-bound + precision-sensitive — verify carefully).
2. int4 dequant micro-opts (folded bias, vec4 u32→int4 unpack, threadgroup weight staging).
3. Subgroup (non-matrix) GEMM — subgroups ARE on Adreno; reduce/broadcast for weight sharing.
4. Subgroup-matrix — capability-probe only; likely unavailable on the phone today.
5. Texture-backed tensors — ultimate mobile lever, full rewrite, defer.
