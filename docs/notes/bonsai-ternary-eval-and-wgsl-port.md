# reference_bonsai-8b-eval

> Bonsai (PrismML ternary LLM): Q1_0 merged upstream, Q2_0_g64 runs on mainline llama.cpp CPU/Metal/Vulkan as of 2026-07

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

Evaluated 2026-06-15. **Bonsai 8B** = PrismML's end-to-end 1-bit (ternary, BitNet-lineage) 8.2B model, ~1.15 GB GGUF. Vendor-reported avg 70.5 (MMLU-R/MuSR/GSM8K/HE+/IFEval/BFCL) — between Llama 3.1 8B (67.1) and Mistral3 8B (71.0), below Qwen3 8B (79.3). **All numbers are first-party; no independent verification found.**

**Verdict: do NOT adopt for TabInfer today — no browser path.** GGUF uses custom `Q1_0 (g128)` format + inline dequant kernels that ONLY exist in PrismML's *fork* of llama.cpp (Mintplex-Labs/prism-ml-llama.cpp). Model card states it does NOT work with upstream llama.cpp → therefore not wllama/WASM. Backends: CPU/Metal/CUDA done, Vulkan/ROCm in dev, MLX build is Apple-native. No WASM/WebGPU/ONNX/MLC. This is a *different* format from the TQ2_0/I2_S BitNet path in [[reference_wllama-webgpu-crash]].

**UPDATE 2026-07-20: fork-only status is OBSOLETE.** Q1_0 fully merged upstream; Q2_0 (ternary, group-64 = 2.25 bpw official format) runs on mainline llama.cpp CPU/Metal/Vulkan (CUDA in review). Use `*-Q2_0_g64.gguf` files from prism-ml HF (1.7B/4B/8B/27B available). See ggml-org/llama.cpp discussion #22019. Native test on i5-1235U recommended (8B ≈ 2.3 GB weights); WASM path still unverified.

**PORT RESEARCH 2026-07-20 (WGSL ternary kernels for TabInfer):**
- **Arch = dense `Qwen3ForCausalLM` / model_type `qwen3`** for 1.7B/4B/8B (verified from unpacked HF configs: all layers full_attention, GQA 8 KV heads, head_dim 128, tied embeds, Qwen vocab 151669, YaRN ×4 rope_scaling — engine must honor YaRN past orig ctx). Existing TabInfer dense-Qwen3 path covers everything except weight format. 27B = Qwen3.6 base, GGUF arch `qwen35` (GDN?) — verify before touching. Unpacked repos ship f16 safetensors → can repack to custom GPU layout, no need to parse llama.cpp Q2_0 blocks.
- Family: 1.7B ternary 0.45GB (avg 0.65, acc/GiB 1.44 vs Qwen3.5-0.8B's 1.13), 4B 0.86GB, 8B 1.75GB (avg 75.5), 27B 7.6GB; binary variants ~35% smaller, ~5-8 pts worse. All first-party numbers.
- **Kernel plan (agent-researched, ranked): Q2 ternary unpack→int8→DP4A GEMV for decode (≈2× vs int4 from bandwidth, ~40-60 tok/s est. 1.7B on Iris Xe) ≫ same unpack feeding existing DP4A tiled GEMM for prefill (10-40%) > Q1 bitplane-popcount GEMV (countOneBits; benchmark vs simple unpack first) > zero-group skip (measure density first) ≫ LUT = DON'T** — GPU software LUT loses both regimes (no PSHUFB equivalent in WGSL; LUT-Tensor-Core paper shows sw-GPU-LUT catastrophic at GEMM); the CPU vlut prefill win does NOT transfer. llama.cpp Vulkan Q2_0 (PR #25430, merged 2026-07-17, g64) independently chose dequant-then-dot with rows-per-workgroup tuning. Activations: keep existing per-token int8 path (BitNet W1.58A8 canonical; llama.cpp CPU does same). Mainline g64 vs PrismML-fork g128 block layouts differ — irrelevant if repacking from safetensors.
- 27B local test on i5-1235U FAILED usefully: 16GB RAM machine had <2GB free → disk thrash, 0.5-0.7 tok/s both backends. Not a format problem.

**SPIKE RESULT 2026-07-20: Bonsai-1.7B ternary RUNS E2E in the sandpie WebGPU engine (unmodified) at 14.7 tok/s decode on Iris Xe** via lossless int4 repack (ternary {-s,0,+s} survives symmetric int4 exactly). Quality on 4-probe battery ≈ Qwen3-1.7B Q4 (math+JSON+extraction ✓, knowledge facts shaky). Harness: untracked `bonsai-test.html` (fetch monkey-patch redirects Qwen3-1.7B HF root → `/_bonsai17/`, OPFS disabled to protect the real quant cache) + scratchpad `repack_bonsai.py` (f16→BF16 projections, materialize lm_head — HF repos ship it even when tied, pad vocab 151669→151936, 6 shards so the chunked loader avoids big allocs). **Gotcha that cost an hour: numpy `astype(np.float16)` ≠ `view(np.float16)` — numeric-converted bits → q_proj max 771k → f16 overflow → all-"!"; `_stageProbe` found it in one shot.** CPU llama.cpp same probes: ternary 1.5-4 t/s, Q1_0 binary surprisingly good (3/4 ✓, 12.6 t/s, 248MB). Remaining work = ternary WGSL kernel (unpack→int8→DP4A) for 2× decode + 0.5GB download.

**TERNARY WGSL KERNEL BUILT 2026-07-20** (untracked `bonsai-ternary-kernel.html`, standalone via TabInferWebGPU engine-core API): decode GEMV, 16 codes/u32 swizzled (weight k=16w+4s+b at bits 8b+2s → `(p>>2s)&0x03030303` gives 4 codes in byte lanes), f16 scale per g=64, structure cloned from engine GEMVDP4 (WG=64 threads share NR rows, x read once/word, tree reduce, 2D grid >65535). **Key optimization: (c−1)·x = c·x − Σx — dot raw {0,1,2} codes via dot4I8Packed and subtract precomputed per-word activation sum (int8-exact, shared across rows) — no sign-decode ALU at all.** Results on Iris Xe (RAM-starved machine, GPU-timestamped): correctness exact (relErr 5.6e-8 vs CPU int ref); lm_head 151936×2048 **2.0× vs int4 DP4A** (3.0ms vs 6.1ms, ~29 GB/s eff ≈ roofline); q_proj 1.1-1.3×; gate/up+down ~0.8-1.0× (launch-bound at 0.5MB weights in standalone bench — real forward should do better). Lessons: (1) `meta` is a RESERVED WGSL keyword — shader silently no-ops via invalid pipeline, zero console errors; check getCompilationInfo(); (2) first structure (32 threads/row, group-per-thread, WG-wide barrier tree) was 40× off roofline — the GEMVDP4 shape (few rows/WG, all threads split K, x reuse) is what makes iGPU GEMV fast; (3) per-byte c−1 without borrow = `((v|0x80808080)-0x01010101)^0x80808080` (superseded by the Σx trick). Integration TODO: ternary variants of fused gateUpSilu + quantized-cache 'tern' kind + repack script emitting 2-bit packs (~0.5GB download for 1.7B).

**WIRED INTO ENGINE (d81f4ba, 2026-07-20):** ternary is now a first-class weight kind in modules/webgpu-qwen3.js — auto-detected at quantize time (bit-exact {-s,0,+s} per QGROUP; early-exit on first 4 rows keeps Qwen3 cost ~zero), stored 16 codes/u32 + f16 scales in the SAME per-32 layout as int4 (all scale indexing shared). Kernels: gemvTern (all N at T=1), gateupTern (fused), gemmTern (prefill = gemmDP4v2 codegen w/ ternary Bs stanza); xsum16 pass rides quantQ8+rmsnormQ for the Σx term. Cache kind 'tern'. __noDp4 → int4 fallback (ternary-exact); __noTernary opt-out. E2E verified: Bonsai-1.7B decode **21.7 tok/s (was 14.7 int4, 1.48×)**, outputs token-identical; Qwen3-0.6B int4 path regression-checked. Model still loads via untracked bonsai-test.html redirect — NOT in the picker; picker entry + hosted repack (~0.5GB 2-bit download instead of 4GB f16) = remaining productization.

**DETECTION FIX + REAL PROFILE (6ffdc4b, 2026-07-20 evening):** the d81f4ba "1.48× verified" claim was WRONG — GPU-ts profile showed int4 labels; ternary had never actually run E2E. Three causes: (1) bit-exact {-s,0,+s} check too strict — PrismML f16 export has rare 1-ULP magnitude wobble (0.002% of elems) → now ≤2-ULP tolerance; (2) gate was __noDp4 which the NOISY perf A/B sets under system load → now gates on _dp4DecodeOk (correctness only); (3) gateUpSiluQ's __noDp4 branch fed tern packs to the int4 f32 kernel → tern branches first. ALSO: harness `window.caches = undefined` silently fails (non-writable) → the compat test POISONED the browser's 'sandpie-webgpu-quant' cache for variant '1.7B' with Bonsai weights (purged; harness now uses defineProperty-throw). True ternary decode profile (Iris Xe, GPU-ts, 41.7ms compute/token, ceiling 24 tps vs int4 49-59ms): gateupTern 16.2ms/38.8% (≈SAME as int4 → ALU-bound, top optimization target), gemvTern.8 q/k/v/o/down 14.2ms (1.4-2× vs int4), lm_head gemvTern.16 3.6ms (1.7×), rmsnormQ 2.4ms, attn 3.7ms, xsum16 0.85ms. Headroom: gateup restructure ~+20-30% total, fuse xsum16 into quantQ8/rmsnormQ, dispatch overhead gap (real tps ≈ 0.8× ceiling on quiet machine).

**PERF PASS (a5cc3ca):** gateupTern NR 2→8 (sweep: NR1 29.0/NR2 16.5/NR4 15.3/NR8 10.8/NR16 16.5-20 ms per token — was ALU-bound at NR2, 1.5×) + Σx fused into QUANTQ8/RMSNORMQ (xsum16 pass deleted, −113 dispatches/token, free for int4 models); __ternGateUpNR/__ternGemvNR runtime overrides enable NR A/B WITHOUT model reloads. Decode compute 41.7→~35ms/token, ceiling 25-29 tps (machine noise ±20% — all sweeps on loaded box). Remaining headroom: gemvTern q/k/v/o/down 14-16ms is the new top block (already 1.4-2× vs int4; per-32-group scale reads could halve), attn+norms ~5.5ms, dispatch-overhead gap real≈0.8×ceiling.

**KERNEL v2 (78457b3):** #2 from the reanalysis DONE. gemvTern2 + gateupTern2 = vec2<u32> weight loads (32 weights = 1 scale group/iter, no index division) + subgroupAdd reduce replacing the shared-mem tree (that barrier dominated the many small q/k/v/o dispatches). GPU-ts A/B on Iris Xe, output byte-identical: gemvTern ~19→14ms, gateupTern ~10→8.7ms, total decode compute ~38→~29ms, ceiling 26→~33 tok/s. Default v2; `__ternGemvV1` reverts BOTH kernels. Roofline for 1.7B on Iris Xe ~11-14ms/token (560MB/tok ÷ ~40-50GB/s) → still ~2× headroom (small q/k/v shapes under-saturate).
