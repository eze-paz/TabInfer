- **FINAL VERDICT = SHELVE the WASM LUT fork.** Technical thesis is sound in theory (AVX_VNNI=0 → LUT/swizzle should beat dequant; WASM TQ2_0 is scalar), BUT the reference LUT impl (Microsoft bitnet.cpp / T-MAC, Eddie-Wang llama.cpp fork @1f86f058) **won't even run on 2 OSes and 2 kernel configs** — the foundation is too broken to base a hand-written WASM LUT kernel on. Ship the pragmatic track: **Q4_K on wllama (threading+COOP) + LiteRT/Gemma on iGPU**. See [[project_sandpie-local-runtime-strategy]].
- **2026 LUT reproduction options (researched 2026-06-16) if revisiting:** (1) **vlut.cpp** — github.com/Cipherxzc/vlut.cpp, "Vec-LUT" (arXiv 2512.06443, MobiSys-2026), a *clean lightweight llama.cpp extension* (`cmake -B build`), supports BitNet/TriLM/Falcon3 1.58-bit + pre-converted HF models, all CPUs — **the cleanest path to a working native LUT number; try this in WSL**. (2) **T-MAC** — github.com/microsoft/T-MAC, canonical LUT lib (bitnet.cpp's TL1/TL2 derive from it), but **ARM-first; explicitly does NOT guarantee x86 speedup** (memory bandwidth) + heavy TVM build. Our bitnet.cpp failures (const patch `ggml-bitnet-mad.cpp:811`, setup_env tokenizer/kernel bugs, TL2 segfault) are **DOCUMENTED known issues**, not our error.
- **vlut.cpp RAN SUCCESSFULLY (2026-06-16) — FIRST working LUT, and it MEASURED the thesis.** Built clean on WSL/Ubuntu-24.04 clang-18 (NO patches, unlike bitnet.cpp), `tiiuae/Falcon3-1B-Instruct-1.58bit` (1.67B), 8 threads, same binary: **I2_V_4 (LUT) vs TQ2_0 (dequant) → PREFILL pp512 = 138.5 vs 88.9 t/s (LUT 1.56× FASTER); DECODE tg64 = 6.4 vs 27.3 t/s (LUT 4.3× SLOWER).** So Vec-LUT is a PARALLEL/PREFILL accelerator, NOT a decode accelerator (matches its README — single-decode LUT is T-MAC's domain, still unvalidated/heavy-TVM). Steps: `python convert_hf_to_gguf_vlut.py <model> --outfile x.vlut.gguf` → `llama-quantize x.vlut.gguf I2_V_4` → `llama-bench -p 512 -n 64`.
- **Thread-sweep (1/2/4/8) CONFIRMS it's the roofline regime, not a threading artifact.** Both kernels multithread on both phases. LUT WINS prefill at every thread count (pp512: 89→143 t/s vs dequant 35→69); dequant WINS decode at every count (tg64: 12→24 vs LUT 4.5→6.2). Decode **plateaus by 4 threads** (memory-bandwidth-bound) while prefill keeps scaling (compute-bound) — exactly the GEMM(M=512)-vs-GEMV(M=1) arithmetic-intensity story. The split holds even at 1 thread, so it's the kernel/regime, not parallelism. **CORRECTION:** the i5-1235U actually HAS **AVX-VNNI** (WSL `/proc/cpuinfo`); the earlier bitnet "AVX_VNNI=0" was a *build* artifact (Eddie-Wang fork not compiling it), NOT a CPU limit — vlut's modern build uses VNNI, so dequant decode (24 t/s) is VNNI-accelerated, making LUT's decode loss even more decisive and weakening the original "chip lacks VNNI → LUT wins" premise.
- **DATA-BACKED FINAL VERDICT: WASM LUT fork = WRONG fit for sandpie's single-user CHAT.** Chat is decode-heavy, and LUT *loses* decode 4.3× to the dequant path (Q4_K/wllama) we already ship. LUT only pays off for **prefill-dominated / batched / serving** workloads. So shelve the fork; ship **Q4_K on wllama (threading+COOP) + LiteRT/Gemma on iGPU**. (Still no WASM LUT exists; vlut/T-MAC are native-only.)
