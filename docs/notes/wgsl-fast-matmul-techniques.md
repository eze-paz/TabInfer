# wgsl-fast-matmul-techniques

> How SOTA in-browser LLM engines do fast int4 matmul in WGSL, and which techniques are portable to our targets (Iris Xe / Adreno)

_Design note written during development (sandpie session memory); names like `TabInfer*` refer to the pre-extraction identifiers, now `TabInfer*`._

Researched 2026-06-21 (3 parallel web agents) for the [[sandpie-webgpu-engine]] prefill-speed problem. Full doc: artifact "WGSL Matmul Reinterpretation".

**Subgroup-matrix / cooperative-matrix (tensor-core-class GEMM) is NOT usable on our targets.** `chromium-experimental-subgroup-matrix` needs desktop NVIDIA/AMD/Arc on Dawn-**Vulkan**, is not in stable Chrome (origin trial ~through Chrome 145), no D3D12 (so most Windows excluded), absent in-browser on mobile, and **absent on Intel Iris Xe gen-12lp** (needs Arc XMX). Do NOT build on it; wire only as an opportunistic path gated on non-empty `GPUAdapterInfo.subgroupMatrixConfigs`.

**Every shipping in-browser engine (WebLLM/MLC·TVM dlight, transformers.js/ORT-web `MatMulNBits`, ggml-Vulkan scalar path, MLDrift) uses the SAME portable recipe** — and our `gemmQ` already has ~80%: 3-level blocking (workgroup→subgroup/warp→register tile), dequant fused into the shared-mem load, inline nibble unpack (`unpack4xU8`/`&0x0F0F0F0Fu`), deferred per-group scaling, f16-multiply/f32-accumulate. Our gaps: (1) **bank-conflict `+1` pad** on shared tiles (cheapest win), (2) the **subgroup/warp middle tile tier** (32×32) we skip, (3) **int8+`dot4I8Packed` (DP4A) integer path**, (4) `subgroupAdd` GEMV reduction for decode.

**MOBILE LANDMINE — f16 is absent on Adreno.** `shader-f16` requires Vulkan `uniformAndStorageBuffer16BitAccess` = **0% of Qualcomm**. Our `gemmQ` is f16-based (`enable f16`, `vec4<f16>` tiles, `sc: array<f16>`) → on the phone it's unavailable/emulated, a prime slowness suspect. **Adreno's only fast quantized path = int8 acts + int4 weights → `dot4I8Packed`(signed, core WGSL feature `packed_4x8_integer_dot_product`, Chrome 123+, DP4A-accelerated) → i32 accumulate → f32 scale per group of 32.** No int4 dot primitive (unpack nibbles→int8 first); no f16/16-bit packed dot exists. int8+DP4A ~1.7–2.9× over f16 on desktop too.

**Decode (GEMV):** 1 subgroup per output row, lanes stride K, one `subgroupAdd` — zero `var<workgroup>` (Adreno-safe; matches the device-loss fix). Loop on runtime `subgroup_size`, never hardcode 32. Adreno subgroup size 64/128, compute-stage only.

**ADRENO maxStorageBufferBindingSize ~128-256MB → an oversized storage binding SILENTLY returns ZEROS (WebGPU validation drop, not a throw).** The dense Qwen3 engine kept embed_tokens as f16 (vocab*H*2 = 311MB for 0.6B) → over Adreno's limit → the embed GATHER returned all zeros → every layer 0 → logits 0 → argmax→token 0 = all-"!". Iris Xe (multi-GB limit) masked it. Diagnosed via an on-phone probe (embedOut=0). FIXED (commit ca59bb1, webgpu-qwen3 v43): quantize embed to int4 (~78MB) + int4 embedGatherQ (ported from hybrid; the hybrid already used int4 embed, which is why IT worked on the phone). 0.6B int4 embed ~78MB fits any Adreno; 1.7B ~155MB needs the 256MB limit. LESSON: any single weight buffer near/over ~128MB is an Adreno risk — keep big tables int4. **A separate bug (also all-"!"):**
**ADRENO `subgroupAdd` IS WRONG → all-"!" output. Never ship a subgroup GEMV without a fallback.** Adreno (the user's phone) computes `subgroupAdd` incorrectly, so any GEMV that reduces with it produces garbage logits → the model emits "!!!!" every token. The hybrid engine (webgpu-qwen35.js) guards this with `probeSubgroups` (verifies subgroup GEMV vs the portable shared-mem path at load, auto-disables on mismatch). The DENSE engine (webgpu-qwen3.js) shipped to the app WITHOUT that guard (Phase-1 code) and hit all-"!" on the phone — FIXED v41 (commit 544f52f) by converting its 3 int4 forward kernels (gemvQ, matvecQ, gateUpSiluQ) to the portable shared-mem tree reduction (no subgroups; GEMV_WG=64 power-of-2). Validated vs CPU ref on Iris Xe (4e-6). LESSON: subgroup reductions are an opt-in fast path that MUST be probe-gated or avoided; the portable tree reduce is the universally-correct baseline. (The leftover subgroupAdd in gemv/matvecT is self-test-only, not on the forward path.)

**Honest scope:** all of this is the GEMM (q/k/v + MLP — bulk of prefill FLOPs). It does NOT touch the 18-layer DeltaNet serial scan, which may be co-dominant. MUST measure GEMM-vs-DeltaNet split + phone caps (shader-f16/subgroups/packed-dot, both on the caps test page) BEFORE building. See [[webgpu-mobile-device-loss-prefill]], [[litert_mldrift_gpu_techniques]].

Build order: (1) measure caps + profiled per-kernel µs on phone; (2) cheap+portable: bank-pad GEMM + subgroupAdd decode; (3) int8/DP4A path (mobile-critical), feature-gated; (4) chunkwise-parallel gated-delta only if DeltaNet measured co-dominant.

**SHIPPED (2026-06-21):** f16-dot gemmQ (v74, probe-verified rel 9e-4 on Iris Xe); coop-matrix gemmQ wired but inert everywhere we can reach (v75, probe-gated on non-empty subgroupMatrixConfigs — empty on Iris Xe AND Adreno, as predicted); bank-pad (v76) — MEASURED a ~10% REGRESSION on Iris Xe (514 vs 572 GFLOP/s, in-browser via the new `_benchGemmQ` export), so it's now a load-time PERF PROBE (probeGemmPad: correctness-verify padded==unpadded, then bench both, enable only if >3% faster). Lesson: the "+1 pad = double-digit win" advice was a double-digit LOSS here — always measure per-device, don't assume. subgroupAdd GEMV (#4) was already shipped + probeSubgroups-gated. **NOT yet done: #3 int8/DP4A (the real Adreno lever — f16 is absent on Qualcomm so the shipped f16 path likely doesn't even help the phone) and #2 32×32 subgroup tile (deferred: untestable, subgroup-correctness-dependent).**

**PREFILL BOTTLENECK = DeltaNet serial scan, NOT the GEMM (measured 2026-06-21).** _benchDelta on Iris Xe: the 18-layer gated-DeltaNet sequential recurrence = ~566ms at T=256 vs ~3ms for the biggest single GEMM — ~190×/layer. We'd been tuning the already-fast parallel GEMM. Built CHUNKWISE-PARALLEL gated-DeltaNet for prefill (v78, commit 43075e6): within a chunk of C=16 all tokens read the same S_in (serial chain T→T/C); exact UT/forward-solve form for THIS engine's recurrence (S_out=Γ(S_in+KᵀΔ̃); o=γ(S_inᵀq+Σ QK·Δ̃); Δ̃=(I+diag(β)M)⁻¹β(Ṽ−K S_in), ṽ=v/γ). Built test-first: CPU ref == GPU sequential to 1.1e-6, chunkwise == CPU ref to ~2-4e-6. Probe-gated (probeDeltaChunk; falls back to sequential deltaRecur on mismatch/SLM-fail). Decode (T=1) UNTOUCHED (stays sequential — 45 tok/s safe). **MEASURED only ~1.6× on Iris Xe** (T=256: 564→347ms) — occupancy-bound at 16 workgroups (1/head). The full 10× needs the matmul-decomposed / val-tiled HIGH-OCCUPANCY form (batch heads×chunks as GEMMs); Adreno may gain more (more idle lanes wasted by the serial scan). Exports: _selfTestDelta, _setDeltaChunk, _probeDeltaChunk, _benchDelta({chunk}).

**v79 (commit 7fb4a26) — 3 of 4 follow-up prefill levers are MEASURED NO-OPS on Iris Xe (kept honest, default-off, exposed for Adreno):** (#1 occupancy) val-tiling the chunkwise kernel (VT=val cols/workgroup, more workgroups) is a LOSS on Iris Xe — VT=32 2.5× slower, VT=16 6× slower (redundant tile reloads; NOT workgroup-occupancy-bound). Kept VT=128 (the 1.63× stands; the real 10× needs matmul-decomposition, a separate rewrite — batch heads×chunks as GEMMs). `_setDeltaVT` exposed for Adreno. (#3) parallel conv prefill (drop serial t-loop) = BIT-IDENTICAL but 1.01× (conv's 6144 channels already saturate; never a bottleneck); `_setConvPar`, default off. (#4) attention already fine: 1 workgroup/(token,head) (~19k wgs @T2400), per-query softmax in SLM, no global T×T materialization → no flash rewrite needed. (#5) f16/int8 ACTIVATIONS pointless for prefill: GEMM is compute-bound ~100× (614 GFLOP/s, ~6MB moved) — only a full int8+DP4A path (weights+acts) would matter, that's the separate Adreno lever. LESSON: measure each lever per-device with the isolated _bench*/_selfTest* exports before shipping; most "obvious" GEMM/occupancy tweaks were no-ops or losses here.

**v80 (commit 8ca9840) — THE prefill diagnosis (why prefill takes ~1 min while decode matches llama.cpp):** Prefill per-token ≈ DECODE per-token because 18/24 layers are the serial gated-DeltaNet recurrence, which gets ZERO batching benefit (a recurrence is inherently serial). 2500 tok × ~20ms/tok ≈ ~50s. The user's llama.cpp comparison (Qwen3.5-**2B-Q4_K_M**) is (a) DENSE — no DeltaNet, fully-parallel prefill — and (b) on CPU (wllama), where serial scans are cheap (high IPC, SIMD, cache-resident state). I READ llama.cpp's gated_delta_net.cu: it's ALSO a token-by-token serial scan (`for t in n_tokens`) with `//TODO: Add chunked kernel for even faster pre-fill` — so they have NO magic parallel delta; their speed = CPU-friendliness + dense model + n_ubatch=512 batching. The DeltaNet scan is GPU-HOSTILE (serial dependency, only 2048 lanes busy). Built the matmul-decomposed chunkwise (deltaChunk2, the FLA-style high-occupancy form, validated vs CPU ref 1-5e-6) — MEASURED 3× SLOWER than v78 on Iris Xe (memory-bound on M/QK/skv/sqv/Δ̃ global round-trips; 80-EU iGPU favors v78's data-local single kernel). So the delta scan is at its iGPU ceiling (~1.55× via v78; THREE occupancy approaches lost). deltaChunk2 kept behind `_setDeltaImpl('matmul')` for Adreno A/B. **CONCLUSION: a faster delta kernel can't fix prefill on this iGPU — the architecture caps it. The decisive lever is WORK ELIMINATION = prefix-cache the static ~2500-tok system prompt (prefill once, snapshot DeltaNet state + attn KV + conv state, reuse every turn). The engine already has snapCopy/_snapIds for in-session prefix reuse — extend it to prime/persist the static system+tools prefix.** This is the next build. LESSON: prefill is ~half scan / ~half GEMM on Iris Xe, GEMM near roofline → even a perfect scan fix is ~2× total there; 10× total prefill needs work-reduction (prefix prewarm/cache of the ~2.4k-tok tool preamble) too. `_benchGemmQ`/`_setGemmPad`/`_setF16Math`/`_setCoopMat`/`_probe*` all exported for per-device A/B on the [[webgpu-mobile-device-loss-prefill]] /sdk harness.
